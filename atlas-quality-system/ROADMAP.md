# Atlas 质量保障体系 - 8 周实施路线图

> **目标**：在 8 周内，从"完全没有质量保障"演进到"具备完整、自动化、可持续的质量体系"
> **适用对象**：业务团队 + AI 协作开发，无专职技术人员
> **核心原则**：**先止血，再补强，再优化**——不要一次性做完所有事

---

## 阅读这份路线图前

### 前提条件

在开始之前，确保以下条件已就绪：

1. ✅ Atlas 项目已有代码仓库（Git 仓库）
2. ✅ 已有部署流程（哪怕是手动的）
3. ✅ 已确定一位"AI 代码守护人"（团队中最懂技术的人，可兼职）
4. ✅ 已阅读过本质量体系的总体方案（`docs/01-总体方案.md`）
5. ✅ 团队已认可"质量需要投入"的理念

### 时间投入预期

- **AI 守护人**：第 1 周 50% 时间，第 2-4 周 30%，第 5-8 周 20%
- **业务开发人员**：第 1 周新增 20% 工作量，逐步降低
- **业务负责人**：每周 1-2 小时审视进展

### 不要做的事

- ❌ **不要并行启动多个阶段**——按顺序完成
- ❌ **不要追求完美**——每个阶段做到 80% 就进入下一阶段
- ❌ **不要省略任何阶段**——每个阶段都是后续的基础
- ❌ **不要在 8 周内完成所有事**——这是不现实的

---

## 整体路线概览

```
Week 1：紧急止血（最高优先级）
  └─ 防止系统继续恶化，建立最低安全网

Week 2：基础设施
  └─ 工具链、CI/CD、规范文档

Week 3：开发流程
  └─ 标准化工作流，业务人员熟练使用

Week 4：测试体系（一）
  └─ 单元测试 + 静态分析 + AI 代码审查

Week 5：测试体系（二）
  └─ 集成测试 + E2E 测试 + 视觉回归

Week 6：可观测性
  └─ 日志、监控、错误追踪、告警

Week 7：发布与应急
  └─ Feature Flag、灰度发布、应急演练

Week 8：体系巩固
  └─ 月度审计、文档完善、团队对齐
```

## Week 1：紧急止血

### 目标
**让 Atlas 不再继续恶化**。如果这一周后必须立刻上线，至少有最低限度的安全网。

### 当周任务

#### Day 1-2：基础保护

- [ ] **任命 AI 代码守护人**
  - 明确职责（参考 `docs/01-总体方案.md` 的"AI 代码守护人"章节）
  - 在团队公布
  - 调整该同事的工作分配（释放至少 50% 时间）

- [ ] **设置 Git 分支保护**
  - 在 GitHub 仓库的 Settings → Branches 中：
    - 主分支（main）禁止直接推送
    - 必须经过 Pull Request
    - 必须经过至少 1 个人审查
    - 必须 CI 通过
    - 启用"Require linear history"

- [ ] **撤销危险权限**
  - 检查应用使用的数据库账号是否有 `DROP TABLE`、`TRUNCATE`、`DELETE` 全表权限
  - 如有，立刻收回（创建受限账号）
  - 检查生产环境密钥是否在代码仓库中（用 `git log --all -p | grep -i "password\|secret\|api_key"`）
  - 如有，立刻轮换密钥并清理 git 历史

- [ ] **配置错误追踪（Sentry 最低配置）**
  - 注册 Sentry 免费账号
  - 在前端、后端各集成 Sentry SDK（5 分钟教程）
  - 部署到生产环境
  - 配置 Slack/邮件通知（让 AI 守护人收到告警）

#### Day 3-4：CLAUDE.md 落地

- [ ] **复制 CLAUDE.md 模板**
  - 把 `templates/CLAUDE.md` 复制到 Atlas 项目根目录
  - 根据 Atlas 实际情况填充（项目概览、技术栈、特殊约束）
  - 让全团队读一遍，提出修改意见

- [ ] **强制使用 CLAUDE.md**
  - 在团队 Wiki / 群公告中：**让 Claude 写代码时，必须先粘贴 CLAUDE.md**
  - 创建一个浏览器书签或快捷指令，方便复制
  - AI 守护人在 PR 审查时，明确询问"是否使用了 CLAUDE.md"

#### Day 5：检查清单试用

- [ ] **打印《提交代码前检查清单》**
  - 物理打印一份，贴在每个开发者桌前
  - 数字版固定在团队 Wiki 的最显眼位置

- [ ] **第一次实战**
  - 在第一个 PR 中，业务开发人员尝试走完整个清单
  - AI 守护人复盘：哪里卡住了？哪里跳过了？
  - 根据反馈微调清单（删除不适用的，补充遗漏的）

### 当周验收标准

- ✅ AI 代码守护人已就位，团队都知道
- ✅ 主分支不能被直接推送
- ✅ 所有密钥不在代码仓库
- ✅ Sentry 能收到生产环境的错误
- ✅ CLAUDE.md 已生效
- ✅ 至少 5 个 PR 走过提交前清单

### 当周风险

⚠️ **业务开发人员抵触新流程**：
- 应对：让他们体验"AI 代码审查发现一个 bug"的成功案例
- 应对：AI 守护人主动协助前 5-10 个 PR，降低门槛

⚠️ **CLAUDE.md 不够具体**：
- 应对：每发现一个 bug，立刻补充到 CLAUDE.md
- 应对：每周五花 30 分钟集中更新一次

⚠️ **找不到合适的 AI 守护人**：
- 应对：可以是兼职，可以是顾问，可以是公司外的技术朋友
- 应对：实在没有，外包给可信的技术服务公司
- **不要**没有守护人就上线——这是底线

## Week 2：基础设施

### 目标
**搭建起所有质量工具的基础平台**：CI/CD、pre-commit、代码规范工具。

### 当周任务

#### Day 1-2：本地开发工具链

- [ ] **配置 pre-commit**
  - 复制 `ci-config/.pre-commit-config.yaml` 到项目根目录
  - 安装：`pip install pre-commit && pre-commit install`
  - 在团队 Wiki 写"如何安装 pre-commit"教程
  - 验证：让所有人本地都能跑起来

- [ ] **配置 ESLint / Ruff / mypy**
  - 前端：复制配置，启用 strict 模式
  - 后端 Python：启用 ruff + mypy strict
  - 修复现有代码的所有问题（**这是体力活**）

- [ ] **配置 .gitignore**
  - 复制 `ci-config/.gitignore`
  - 确保 `.env`、`node_modules`、`__pycache__` 都在里面

#### Day 3-4：CI/CD 基础

- [ ] **搭建 GitHub Actions**
  - 复制 `ci-config/.github-workflows-quality-gate.yml` 到 `.github/workflows/`
  - 第一次运行可能很多失败——逐个修复
  - 让 CI 在 10 分钟内跑完

- [ ] **搭建测试环境**
  - 复制 `ci-config/docker-compose.test.yml`
  - 文档化"如何在本地启动测试环境"
  - 让所有人都能 `docker-compose up` 起一个

#### Day 5：依赖管理

- [ ] **审计现有依赖**
  - 运行 `npm audit` / `pip-audit`
  - 修复所有 high/critical 漏洞
  - 删除未使用的依赖（用 `depcheck`）

- [ ] **建立依赖更新流程**
  - 启用 GitHub Dependabot
  - 配置每周自动 PR
  - 由 AI 守护人审查

### 当周验收标准

- ✅ 本地 pre-commit 在所有人机器上工作
- ✅ CI 在 10 分钟内跑完，全部通过
- ✅ 所有静态扫描问题清零
- ✅ 没有已知的 high/critical 依赖漏洞
- ✅ 任何人都能在本地启动测试环境

### 当周风险

⚠️ **CI 太慢**：
- 应对：并行跑测试（matrix strategy）
- 应对：缓存依赖（actions/cache）
- 应对：只跑变更影响的测试（path-based filtering）

⚠️ **修复存量问题工作量大**：
- 应对：分批修复（每天 30 分钟）
- 应对：优先修复严重的，遗留低严重问题
- 应对：让 Claude 帮忙修复（用 `prompts/02-代码生成提示词.md` + 描述要修的问题）

## Week 3：开发流程

### 目标
**让 14 步标准工作流在团队中跑通**，业务人员能熟练使用所有提示词。

### 当周任务

#### Day 1-2：流程培训

- [ ] **组织全员培训**（2 小时）
  - 讲解 `docs/03-工作流程.md` 的 14 步工作流
  - 演示一个真实需求从 0 到上线的全过程
  - 强调"模板 + 提示词 + 检查清单"的三件套

- [ ] **手把手实战**
  - 选一个真实小需求
  - AI 守护人陪一位业务开发人员走完全流程
  - 每一步都暂停讨论"这步在干嘛、为什么"

#### Day 3-4：模板与提示词试用

- [ ] **使用需求模板**
  - 接下来所有需求**必须**用 `templates/REQUIREMENT_TEMPLATE.md` 编写
  - AI 守护人审核需求文档完整性，不完整不开发

- [ ] **使用提示词库**
  - 在团队 Wiki 整理 7 个提示词的快捷链接
  - 每个提示词对应的场景，让业务开发人员实际用一次
  - 收集反馈：哪个提示词不好用？为什么？

#### Day 5：流程优化

- [ ] **第一次流程回顾**
  - 团队聚一起，列出本周流程中遇到的痛点
  - 哪些步骤太繁琐可以简化
  - 哪些步骤太宽松要加强
  - 更新流程文档

### 当周验收标准

- ✅ 全团队接受过流程培训
- ✅ 所有新需求使用需求模板
- ✅ 7 个提示词都被实际使用过
- ✅ 团队能说出 14 步工作流的关键节点
- ✅ 至少 1 个完整需求按新流程从 0 到上线

### 当周风险

⚠️ **流程太繁琐，业务人员抵触**：
- 应对：先专注核心流程（澄清需求 → 生成代码 → 审查 → 测试 → 上线）
- 应对：允许小修复用简化流程（但仍要有测试）
- 应对：用真实成功案例打动人，而不是讲道理

⚠️ **业务人员不会用提示词**：
- 应对：录制 15 分钟视频教程
- 应对：AI 守护人前几次旁观、辅导
- 应对：把"使用 prompts/03 让 Claude 审查代码"作为强制步骤

## Week 4：测试体系（一）- 单元测试与代码审查

### 目标
**为 Atlas 建立单元测试和 AI 代码审查的基础**。

### 当周任务

#### Day 1-2：测试基础设施

- [ ] **搭建单元测试框架**
  - 后端：pytest + pytest-cov + factory-boy
  - 前端：Vitest + Testing Library
  - 配置覆盖率报告
  - 写"hello world"测试，确保跑通

- [ ] **测试约定**
  - 所有测试放在 `tests/` 目录
  - 使用 AAA 模式（Arrange-Act-Assert）
  - 用 factory 创建测试数据，不要硬编码
  - 测试名称清晰描述场景

#### Day 3-4：补充关键单元测试

- [ ] **识别核心模块**
  - 列出 Atlas 的 Top 10 关键功能
  - 这些功能的核心代码必须有测试

- [ ] **生成测试**
  - 对每个核心功能，使用 `prompts/04-测试生成提示词.md`
  - 让 Claude 生成测试，AI 守护人审查
  - 目标：核心模块覆盖率 ≥ 80%

#### Day 5：AI 代码审查集成

- [ ] **集成 AI Code Review**
  - 在 CI 中加入"AI 代码审查"步骤
  - 调用 Claude API 用 `prompts/03-代码审查提示词.md` 审查 PR
  - 把结果作为 PR 评论
  - **本周先不强制**，作为辅助参考

- [ ] **观察审查质量**
  - AI 守护人对比"AI 审查 + 自己审查"的结果
  - AI 报出来但守护人不认同的 → 调整提示词
  - 守护人发现但 AI 没报的 → 调整提示词

### 当周验收标准

- ✅ 单元测试框架就绪，CI 中跑测试
- ✅ 核心模块覆盖率 ≥ 80%
- ✅ AI Code Review 在 CI 中运行
- ✅ 至少有 50 个单元测试

### 当周风险

⚠️ **测试维护成本高**：
- 应对：测试代码也要简洁、有可读性
- 应对：避免过度模拟（mock everything），保持测试贴近真实
- 应对：定期重构测试代码

⚠️ **AI 审查噪音多**：
- 应对：迭代提示词，让它更精准
- 应对：先聚焦 🔴 阻断性问题，🟡 建议项可以静默
- 应对：让 AI 给出"理由"，便于人类判断

## Week 5：测试体系（二）- 集成测试与 E2E

### 目标
**让真实的用户旅程被自动化测试覆盖**。

### 当周任务

#### Day 1-2：集成测试

- [ ] **API 集成测试**
  - 用 pytest + httpx（后端）测试 API 端点
  - 用 Testcontainers 启动真实 PostgreSQL
  - 覆盖所有关键 API（认证、核心 CRUD、特殊业务逻辑）

- [ ] **数据库测试**
  - 测试数据库迁移可以正反执行
  - 测试索引在大数据量下有效
  - 测试事务边界正确

#### Day 3-4：E2E 测试

- [ ] **搭建 Playwright**
  - 安装 Playwright
  - 配置多浏览器（Chromium、Firefox、Webkit）
  - 写第一个测试：用户注册 → 登录 → 退出

- [ ] **覆盖核心用户旅程**
  - 列出 Atlas 的 5-10 个最重要用户旅程
  - 每个写一个 E2E 测试
  - 让测试在 CI 中跑（每次 PR）

#### Day 5：视觉回归 + 可访问性

- [ ] **视觉回归测试**
  - 集成 Percy 或 Playwright 的截图对比
  - 对核心页面建立基线
  - PR 中自动检查视觉变化

- [ ] **可访问性扫描**
  - 集成 axe-core 到 E2E 测试中
  - 修复 critical 问题
  - 把 axe 检查纳入 CI

### 当周验收标准

- ✅ 至少 20 个集成测试
- ✅ 至少 10 个 E2E 测试覆盖核心旅程
- ✅ 视觉回归测试在运行
- ✅ 可访问性扫描在运行
- ✅ E2E 测试跨 3 种浏览器

### 当周风险

⚠️ **E2E 测试容易 flaky**：
- 应对：永远用 `expect().toBeVisible()` 而不是 `sleep()`
- 应对：每个测试独立，不依赖其他测试的状态
- 应对：失败重试 1-2 次（CI 配置）
- 应对：建立"flaky 测试隔离区"，定期修复

⚠️ **测试速度慢**：
- 应对：并行执行（Playwright workers）
- 应对：只在 main 分支跑全量，PR 跑核心测试
- 应对：使用测试数据库 snapshot 加速

## Week 6：可观测性

### 目标
**让生产环境的所有问题都能被及时发现**。

### 当周任务

#### Day 1-2：日志体系

- [ ] **结构化日志**
  - 使用 JSON 格式日志（pino / structlog）
  - 每条日志包含：timestamp、level、trace_id、user_id（如有）、message、context
  - 关键路径上加日志（认证、支付、关键业务动作）
  - 严禁日志中出现：密码、token、信用卡号

- [ ] **日志聚合**
  - 选择方案：Loki（自托管）/ Datadog / CloudWatch
  - 配置应用 → 日志聚合的接入
  - 创建几个常用查询（错误日志、慢请求日志）

#### Day 3：监控指标

- [ ] **业务指标埋点**
  - 注册数、登录数、关键操作数
  - 用 Prometheus + Grafana 或 Datadog
  - 创建业务大盘

- [ ] **技术指标**
  - QPS、响应时间（P50/P95/P99）、错误率
  - CPU、内存、磁盘、网络
  - 数据库 QPS、连接数、慢查询
  - 创建技术大盘

#### Day 4：告警

- [ ] **业务告警**
  - 注册失败率 > 5%
  - 关键页面 5 分钟无访问
  - 支付成功率下降 > 5%

- [ ] **技术告警**
  - 错误率 > 1%
  - P95 响应时间 > 1s
  - CPU > 80%
  - 磁盘 > 80%
  - SSL 证书 < 30 天到期

- [ ] **告警通道**
  - 配置 Slack / 钉钉 / 微信 webhook
  - 紧急告警 → 电话/短信
  - 一般告警 → 邮件/IM
  - 测试每个告警都能正确触发和送达

#### Day 5：错误追踪深度配置

- [ ] **Sentry 配置完善**
  - 上传 source map（前端能看原始代码）
  - 配置 release 标签（看哪个版本引入的）
  - 配置用户上下文（看哪些用户受影响）
  - 配置面包屑（错误前发生了什么）

- [ ] **APM（应用性能监控）**
  - 集成 Datadog APM / New Relic / 自托管 Tempo
  - 看请求全链路（前端 → 后端 → 数据库）
  - 找出性能瓶颈

### 当周验收标准

- ✅ 所有错误被 Sentry 捕获
- ✅ 业务大盘 + 技术大盘已搭建
- ✅ 关键告警已配置且测试过
- ✅ AI 守护人能在 1 分钟内判断系统是否正常
- ✅ 至少能查询 30 天的历史日志

### 当周风险

⚠️ **告警风暴**：
- 应对：合并同类告警
- 应对：配置告警抑制规则
- 应对：低严重告警不发短信

⚠️ **监控成本高**：
- 应对：根据数据量选合适的方案（小项目用 Loki + Grafana，免费）
- 应对：合理设置数据保留期
- 应对：避免高基数标签（如用户 ID 作为标签）

## Week 7：发布与应急

### 目标
**建立安全发布机制和应急能力**。

### 当周任务

#### Day 1-2：Feature Flag

- [ ] **集成 Feature Flag 系统**
  - 选择：Unleash（开源自托管）/ LaunchDarkly / GrowthBook
  - 在前端、后端集成 SDK
  - 创建第一个 Flag，验证能动态切换

- [ ] **改造现有代码**
  - 给所有"接下来 1 个月内的新功能"加 Flag 包裹
  - 默认关闭，灰度开启

#### Day 3：灰度发布

- [ ] **配置灰度发布**
  - 部署管道支持 Canary（5% → 25% → 50% → 100%）

## 常见情况应对

### 情况 1：业务突然要求紧急上线

**应对**：
- 即使紧急，也**不要**跳过 Week 1 的内容（密钥保护、Sentry、CLAUDE.md）
- Week 2 的 CI 可以简化（先静态扫描+pre-commit，回头补测试）
- Week 4-5 的测试可以聚焦"最最核心"的功能
- 但**绝对不能**没有应急方案就上线（Week 7 的 Feature Flag + 回滚必须先做）

### 情况 2：发现严重问题需要回炉

如果某周中途发现前一周的工作有重大问题（比如发现 CLAUDE.md 完全不被使用）：

**应对**：
- **暂停推进**，回头修
- 修改方法，让它真的有效
- 然后再继续

不要"边做边修"——前面的基础没打牢，后面会塌方。

### 情况 3：团队成员变动

**应对**：
- 所有新人入职后，必须完成"新人质量培训"（半天）
- AI 守护人离职前，必须完成知识交接（至少 2 周）
- 新人前 3 个月的代码，AI 守护人必须**逐行**审查

### 情况 4：进度落后

**应对**：
- 不要砍质量目标（覆盖率、错误率等）
- 要砍范围（少做几个测试，不要降低单个测试的质量）
- 必要时延长 timeline 到 10-12 周
- 业务负责人需要理解"质量投入是必要的"
