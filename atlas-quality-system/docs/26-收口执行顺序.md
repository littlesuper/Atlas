# 收口执行顺序

> 用途：把 Week 8 最后 1% 的命令串成明确顺序，标出当前 active step。它不会替代真实证据，只告诉团队下一步该做什么。

## 生成命令

```bash
npm run quality:closure-sequence --workspace=server
```

默认输出 `QUALITY_CLOSURE_SEQUENCE` JSON。

阻塞项解决判断对应的机器输出为 `QUALITY_BLOCKER_RESOLUTION / RESOLVED`。

证据交接判断对应的机器输出为 `QUALITY_CLOSURE_EVIDENCE_HANDOFF / READY`。

剩余工作清单对应的机器输出为 `QUALITY_CLOSURE_REMAINING_WORK / READY`。

收口请求包对应的机器输出为 `QUALITY_CLOSURE_REQUEST_PACK / READY`。

当前默认顺序：

| 顺序 | 命令 | 当前状态 | 期望状态 |
| --- | --- | --- | --- |
| 1 | `quality:owner-assignments` | `ACTION_REQUIRED` | `ACTION_REQUIRED` |
| 2 | `quality:blocker-resolution` | `ACTION_REQUIRED` | `RESOLVED` |
| 3 | `quality:closure-evidence-pack` | `READY` | `READY` |
| 4 | `quality:closure-evidence-handoff` | `READY` | `READY` |
| 5 | `quality:closure-remaining-work` | `ACTION_REQUIRED` | `READY` |
| 6 | `quality:closure-request-pack` | `ACTION_REQUIRED` | `READY` |
| 7 | `quality:evidence-intake -- --confirm ...` | `ACTION_REQUIRED` | `READY_TO_CONFIRM` |
| 8 | `quality:team-confirmations -- --confirm ...` | `PENDING` | `CONFIRMED` |
| 9 | `quality:final-closure -- --artifact ...` | `PENDING` | `READY_TO_ARCHIVE` |
| 10 | `quality:progress-guard -- --evidence quality:closure-sequence --changelog quality:closure-sequence` | `PENDING` | `READY` |

## 当前卡点

默认 active step 是 `blocker resolution`：需要先确认三条阻塞项是已清除还是已被显式接受。当前 `closure evidence pack` 和 `closure evidence handoff` 已是 `READY`，后续通过 `quality:closure-remaining-work` 汇总剩余 4 项，再用 `quality:closure-request-pack` 生成 owner 请求文本，之后进入 evidence intake、团队确认和最终归档。

## 自定义步骤

```bash
npm run quality:closure-sequence --workspace=server -- \
  --step "evidence intake|npm run quality:evidence-intake --workspace=server -- --confirm ...|READY_TO_CONFIRM|READY_TO_CONFIRM|AI 代码守护人" \
  --step "final closure|npm run quality:final-closure --workspace=server -- --artifact ...|READY_TO_ARCHIVE|READY_TO_ARCHIVE|AI 代码守护人"
```

每个 `--step` 的格式：

```text
name|command|status|expectedNextStatus|owner
```

当所有步骤都达到 `expectedNextStatus` 时，输出 `READY_TO_ARCHIVE`。
