# Atlas 可观测性与告警矩阵

> 目标：让线上问题可以被发现、定位和复盘。当前策略是先用 Pino/requestId + Sentry 错误追踪形成最小闭环，再逐步补业务指标、技术指标和告警通道。

## 环境变量

| 变量 | 作用 | 必需性 |
| --- | --- | --- |
| `SENTRY_DSN` | 服务端错误上报 DSN | 生产建议必填 |

| `SENTRY_RELEASE` | 服务端 release 名称，也可供前端构建复用 | 生产建议必填 |
| `VITE_SENTRY_DSN` | 前端错误上报 DSN | 生产建议必填 |
| `VITE_SENTRY_TRACES_SAMPLE_RATE` | 前端性能采样率，默认 `0` | 可选 |
| `VITE_APP_VERSION` | 前端事件 release 名称 | 生产建议必填 |
| `SENTRY_AUTH_TOKEN` | 上传 source map 的 Sentry token | 仅发布构建需要 |
| `SENTRY_ORG` | Sentry 组织 slug | 仅发布构建需要 |
| `SENTRY_PROJECT` | Sentry 项目 slug | 仅发布构建需要 |
| `METRICS_TOKEN` | 生产环境访问 `/api/metrics` 的 token | 生产必填 |
| `SLOW_REQUEST_THRESHOLD_MS` | 慢请求统计阈值，默认 `1000` | 可选 |
| `ALERT_WEBHOOK_URL` | `alerts:check` 发送告警的 webhook 地址 | 至少一个告警通道上线前必填 |

| `INCIDENT_BASE_URL` | `incident:collect` 默认采集的 Atlas API 地址 | 可选 |
| `INCIDENT_REQUEST_ID` | `incident:collect` 默认关联的 requestId | 可选 |
| `RELEASE_BASE_URL` | `release:precheck` 默认检查的 Atlas API 地址 | 可选 |

## 告警通道运行方式

```bash
npm run alerts:check --workspace=server
```

脚本会读取 `/api/metrics` 的 `alerts` 数组：没有 active alerts 时输出 `no_alerts` 并正常退出；生产环境如果配置了 `METRICS_TOKEN`，脚本会自动带上 `Authorization: Bearer <METRICS_TOKEN>`。当存在 active alerts 且配置 `ALERT_WEBHOOK_URL` 时，脚本会发送 JSON payload，适合作为 cron、CI 定时任务、云函数或容器定时任务的执行入口。

## 建议告警规则

| 优先级 | 告警 | 触发条件 | 处理建议 |
| --- | --- | --- | --- |
| P0 | 服务端 500 激增 | 5 分钟内同一 issue 事件数 >= 5，或任意 release 500 事件数 >= 10 | 立即查看 Sentry issue，复制 `requestId` 到日志系统检索，同步评估是否回滚 |
| P0 | 前端白屏/渲染错误 | 10 分钟内 `source=ErrorBoundary` 事件数 >= 5 | 查看受影响路由、浏览器和 release；若集中在新 release，优先回滚或禁用相关入口 |
| P1 | API 5xx 客户端感知 | 10 分钟内 `source=api` 事件数 >= 10 | 用事件 tag 中的 `requestId` 关联后端日志，确认是否为单接口或下游依赖问题 |
| P1 | 新 release 错误率升高 | 新 release 30 分钟内 error event 较上一 release 增长 >= 50% | 暂停继续发布，按模块 owner 分派修复 |
| P1 | 数据库健康检查失败 | `/api/health` 连续 3 次返回 `503 degraded` | 检查数据库连接串、磁盘、连接池和最近迁移；必要时暂停发布 |
| P1 | API 5xx rate 升高 | `/api/metrics` 中 `5xx / totalRequests` 10 分钟窗口 >= 2% | 结合 Sentry issue 和 requestId 检索日志，定位集中接口 |
| P1 | 活动导入成功数异常下降 | `activity.import.succeeded` 较近 7 天同周期下降 >= 50% | 检查 Excel 导入解析、权限、模板数据和最近上传错误 |
| P2 | 慢请求增多 | `/api/metrics` 中 slowRequests 占比 >= 10%，或 p95 >= 2000ms | 查看 top routes，优先排查数据库查询和大文件导入/导出 |
| P2 | AI 功能降级 | AI route 出现连续熔断或 5xx >= 5 | 检查 `AI_API_URL`、额度和 circuit breaker 状态，必要时切到规则引擎 |

## 指标采集方式

JSON 快照：

```bash
curl http://localhost:3000/api/metrics
```

Prometheus 文本：

```bash
curl 'http://localhost:3000/api/metrics?format=prometheus'
```

生产环境采集时复用 `/api/metrics` 的 `METRICS_TOKEN` 授权策略：Prometheus scrape job 可配置 `Authorization: Bearer <METRICS_TOKEN>`，或在反向代理层注入 `X-Metrics-Token`。

## 日志检索方式

人工排查：

```bash
npm run logs:request --workspace=server -- <requestId> .logs
```

自动化消费：

```bash
npm run logs:request --workspace=server -- <requestId> .logs --json
```

JSON 输出包含 `requestId`、`filesScanned`、`totalMatches` 和 `matches[]`，后续可以直接接入事故复盘脚本、CI 失败上下文收集或日志平台导入校验。

## 事故上下文采集

基础采集：

```bash
npm run incident:collect --workspace=server -- --base-url http://localhost:3000
```

带 requestId 日志片段：

```bash
npm run incident:collect --workspace=server -- --base-url http://localhost:3000 --request-id <requestId> --logs .logs
```

输出为 JSON，包含 `health`、`metrics`，以及可选 `logs`。这份上下文适合贴入事故复盘、发布失败记录或值班交接。

## 发布前健康门禁

```bash
npm run release:precheck --workspace=server -- --base-url http://localhost:3000
```

脚本会读取 `/api/health` 与 `/api/metrics`，输出 `GO/NO_GO` JSON 报告。以下情况会返回 `NO_GO` 并以非 0 状态退出：

- `/api/health.status` 不是 `ok`
- 数据库健康检查存在且状态不是 `ok`
- `/api/metrics.status` 不是 `ok`
- `/api/metrics.alerts` 存在 active alerts

## 排障路径

1. 从用户反馈或 Sentry issue 获取 `requestId`、release、用户操作页面和时间窗口。
2. 在后端日志中按 `requestId` 检索，确认具体 API、状态码、耗时和错误栈；本地可运行 `npm run logs:request --workspace=server -- <requestId> .logs`，自动化场景追加 `--json`。
3. 如果是前端 ErrorBoundary，先看 component stack 和当前 route，再查同 release 是否集中爆发。
4. 如果是 API 5xx，优先定位最近变更、数据库迁移、外部依赖和权限边界。
5. 修复后补回归测试，并在本文件或事故复盘中记录新增告警或阈值调整。
