# Atlas 质量保障系统:FAQ与故障处理

## 一、流程相关FAQ

### Q1: 我只是改了个文字,也要走全流程吗?

**A**: 是的,不能开特例。

理由:
- "只改个文字"经常引起意外问题(语言切换、CSS布局)
- 一旦开特例,口子越开越大,体系崩溃
- 走流程的成本是10分钟,出问题的成本是10小时

**唯一例外**:文档(`*.md`)的修改可以简化,但代码相关的任何改动都必须走完整流程。

---

### Q2: CI跑得太慢,等不及怎么办?

**A**: 不要等,**让CI跑的同时去做下一个需求**。

CI慢的原因和解决:
- E2E测试多 → 优化:把测试并行化、按变更范围只跑相关测试
- 镜像构建慢 → 优化:用缓存层、用 Docker BuildKit
- 测试本身慢 → 优化:用Testcontainers替代慢的setup、用更快的测试运行器

如果CI持续>20分钟,联系AI代码守护者优化。

---

### Q3: AI Code Review经常误报,怎么办?

**A**: 分两种情况:

**情况1:Claude理解错了上下文**
- 解决:在PR描述中说明背景,或回复Claude解释
- Claude会重新审查

**情况2:Claude发现了真问题但你觉得"无所谓"**
- 解决:**不要无视**。分析Claude的担忧,要么修复,要么找守护者讨论
- 业务人员不是判断"代码对不对"的合适人选

---

### Q4: 我的需求很简单,Claude生成的代码也很短,真的需要这么多测试吗?

**A**: **是的,因为简单的代码也会出bug**。

历史教训:
- 一个空格的代码改动,导致生产宕机 8 小时
- 一行 SQL 的小优化,导致数据丢失
- 一个看似无关的改动,引发连锁反应

**测试的价值不仅是发现当前bug,更是防止未来回归**。

但是,简单的修改写少量测试也是可以的。原则:**修改了什么就测试什么**,不强求覆盖率。

---

### Q5: 业务催得急,能不能跳过Staging直接上生产?

**A**: **绝对不行**。

如果出现这种压力,告诉业务方:
- "跳过Staging导致的事故,损失会比延迟上线大10倍"
- "我们有完善的Canary机制,真正紧急的功能可以快速灰度"

如果业务方仍然坚持,**让他们书面确认承担风险**,并立即升级到部门负责人。

---

### Q6: 部分测试经常失败(flaky test),怎么处理?

**A**: 按以下流程:

```
1. 立即标记为已知问题(在GitHub开issue)
2. 临时retry 2次(Playwright/CI支持)
3. 一周内必须修复或删除
4. 不允许长期容忍flaky测试
```

**严禁**:为了PR过CI而把测试改成不那么严格(降低了真实保障)。

---

### Q7: Claude生成的代码看起来很复杂,我看不懂怎么办?

**A**: 这是好事!说明你警觉了。处理方式:

```
方法1: 让Claude解释
"请用业务人员能理解的语言,解释这段代码做了什么"

方法2: 让Claude简化
"这段代码太复杂,请用更简单的方式重写"

方法3: 让Claude分解
"请把这个函数拆分成多个小函数,每个函数只做一件事"
```

**红旗信号**:
- 嵌套if-else超过3层
- 单个函数超过50行
- 看不懂注释在说什么
- 用了从没见过的库

如果看到红旗,要求Claude重写或找守护者review。

## 二、技术问题FAQ

### Q8: Pre-commit检查总是失败,我每次都要修很多

**A**: 这说明Claude生成的代码不符合规范。改进方法:

1. **检查CLAUDE.md是否完整**:确保规范都写清楚了
2. **生成代码时强调规范**:每次都贴CLAUDE.md
3. **使用专门的提示词**:`prompts/02-代码生成提示词.md` 已包含规范要求

如果还是不行,可能是CLAUDE.md过时了,联系守护者更新。

---

### Q9: 数据库迁移失败,生产数据有风险吗?

**A**: 看具体情况:

**安全的失败**(无风险):
- Migration在Staging失败,根本没到生产
- Migration在生产但是事务回滚了

**有风险的失败**(需立即处理):
- Migration在生产部分成功(比如改了一半表结构挂了)
- 数据丢失或损坏

**应急步骤**:
1. **立即**告诉守护者
2. 不要尝试自己修复(可能造成更大破坏)
3. 守护者会决定:回滚 / 前向修复 / 数据恢复

**预防**:
- 所有Migration必须在Staging充分测试
- Migration必须有 `down` 脚本
- 关键表变更前必须备份

---

### Q10: 测试覆盖率低于70%,但代码已经写完了

**A**: 处理顺序:

1. **先分析未覆盖的代码是什么**
   - 看 coverage 报告,找出红色行
   - 用 `prompts/04-测试生成提示词.md` 让Claude补测试

2. **判断这些代码是否值得测试**
   - 业务核心 → **必须测试**,补到达标
   - 错误处理 → 应该测试,补到达标
   - 简单getter/setter → 可以放过,降低门槛
   - 完全无用的代码 → 删掉

3. **如果合理性证明可以放低标准**,与守护者协商局部降低门槛

---

### Q11: 性能测试发现某个API慢,但我们不知道怎么优化

**A**: 用Claude辅助分析:

```
你: 这是API代码: [代码]
   这是性能测试报告: [报告显示P95=800ms,目标200ms]
   请分析性能瓶颈并给出优化建议。

Claude: 我发现以下问题:
  1. 第15行存在N+1查询:循环中调用了findById
  2. 没有索引: orders表的user_id字段
  3. 没有缓存: 同样的用户信息重复查询
  
  优化建议:
  1. 用findByIds批量查询: [代码示例]
  2. 添加索引: CREATE INDEX...
  3. 添加Redis缓存: [代码示例]
```

性能优化往往是"慢SQL"和"N+1查询"——Claude对这些很在行。

---

### Q12: 安全扫描报了一堆"中危"漏洞,需要全部修吗?

**A**: 分级处理:

| 严重度 | 处理 | 时限 |
|-------|------|------|
| Critical | 必须修 | 24小时 |
| High | 必须修 | 一周 |
| Medium | 评估后决定 | 一个月 |
| Low | 可记录暂不修 | - |

**评估Medium的考虑因素**:
- 是否在生产环境暴露?(内部工具影响小)
- 是否有缓解措施?(WAF、网络隔离)
- 修复成本vs风险

**关键**:不要"因为难修就忽略",找守护者讨论。

---

### Q13: 视觉回归报告显示有差异,怎么判断是bug还是预期?

**A**: 流程:

```
看Chromatic/Percy的对比图
  ↓
预期变化(我做的UI改动)
  → 在工具中点 "Accept" 接受为新基线
  
意外变化(我没改但变了)
  → 这是bug,可能是CSS连锁反应
  → 让Claude分析: "这个改动为什么影响了X页面的样式?"
  → 修复后重新测试

不确定
  → 截图发给守护者judgment
```

**注意**:即使是预期变化,也要确认:
- 文字没截断
- 布局没破坏
- 在不同设备上都正常

---

### Q14: 部署到Staging后,功能在本地正常但Staging出错

**A**: 90%的情况是环境差异。排查清单:

- [ ] 环境变量是否一致?(`.env.example` vs Staging设置)
- [ ] 数据库版本/数据是否一致?
- [ ] 第三方服务是否可达?(API地址、密钥)
- [ ] CORS配置是否正确?
- [ ] HTTPS配置是否正确?
- [ ] 时区/语言设置?

让Claude辅助:
```
你: 本地运行正常,Staging报错: [错误日志]
   Staging vs 本地的差异: [列出已知差异]
   请分析可能原因。
```

## 三、生产事故处理

### 紧急事故响应步骤

如果生产环境出现严重问题:

```
🚨 立即(0-5分钟)
  ↓
1. 不要慌,不要私自修代码
2. 立即在 #incident-response 频道报告
3. 通知"AI代码守护者"
  ↓
🚨 评估(5-15分钟)
  ↓
4. 判断影响范围:
   - 多少用户受影响?
   - 哪些功能不可用?
   - 是否数据问题?
  ↓
🚨 止血(15-30分钟)
  ↓
5. 选择止血方案:
   - 选项A: 关闭Feature Flag(最快)
   - 选项B: 回滚到上一版本(中等)
   - 选项C: 切换到降级方案(复杂)
  ↓
🚨 验证(30-60分钟)
  ↓
6. 确认问题已解决
7. 通知用户(如有必要)
  ↓
🚨 复盘(事后24小时内)
  ↓
8. 写PIR(Post-Incident Review)
9. 把事故场景变成新测试用例
10. 更新CLAUDE.md预防类似问题
```

---

### 常见生产事故处理

#### 事故1:某个功能完全不可用

```
立即:关闭对应Feature Flag
  ↓
日志分析: 找出错误堆栈
  ↓
让Claude辅助分析根因:
"生产错误日志: [日志]
 相关代码: [代码]
 请分析根因并给出修复方案"
  ↓
修复 → 走完整流程 → 重新发布
```

#### 事故2:性能突然变差

```
立即:看监控大盘,定位是哪个服务/接口慢
  ↓
是否最近发布?
  是 → 立即回滚,先恢复再分析
  否 → 看负载情况、数据库情况、外部依赖
  ↓
找Claude分析:
"这个API突然变慢,日志: [日志]
 数据库慢查询: [慢查询]
 请分析可能原因"
```

#### 事故3:数据问题(疑似数据丢失/错误)

**🔴 这是最严重的事故,立即升级**

```
立即:停止所有写操作(关闭服务或降级)
  ↓
不要尝试修复数据!不要尝试修复数据!不要尝试修复数据!
  ↓
联系守护者 + 部门负责人
  ↓
评估恢复方案:
  - 从备份恢复
  - 从日志重放
  - 业务规则修复
  ↓
执行恢复(由守护者操作,不是业务人员)
```

#### 事故4:安全告警(疑似被攻击)

```
立即:看告警详情
  ↓
联系守护者
  ↓
不要私自处理(可能销毁证据)
  ↓
按守护者指示:
  - 隔离受影响系统
  - 收集日志证据
  - 通知用户(如有数据泄露)
```

## 五、关于AI能力边界

### Claude会保证生成的代码无bug吗?

**不会**。Claude会犯错,有时候错得很离谱。

所以本系统的核心是:
- **不依赖Claude不犯错**
- **依赖多重检查机制发现Claude的错**

### Claude能完全替代程序员吗?

**目前阶段不能**。Claude擅长:
- 写常规代码
- 写测试
- Code Review
- 解释问题

Claude不擅长:
- 复杂架构决策
- 业务深度理解
- 性能极致优化
- 新技术探索

所以"AI代码守护者"角色不可替代。

### 是不是AI越来越强,这套体系会失效?

**恰恰相反,AI越强,这套体系越重要**。

因为:
- AI生成代码的速度越来越快
- 业务人员越来越不需要懂代码
- 对应的,**自动化质量保障变得唯一可依赖的防线**

未来的趋势是:
- AI写80%的代码
- AI写80%的测试
- AI做80%的Code Review
- 但**质量体系**和**关键人审**永远是必需的

## 六、寻求外部帮助的标准

什么时候应该找外部专家(咨询/外包)?

### 应该找外部帮助

- 初次搭建基础设施(K8s、CI/CD)
- 安全合规审计(SOC2、等保)
- 性能瓶颈定位(找不到原因)
- 重大架构决策
- 严重生产事故应急

### 不应该找外部帮助

- 日常需求开发(应该业务人员+AI能搞定)
- 写测试用例(用本系统的提示词)
- Code Review(用AI Review)
- 一般性Bug修复

### 选外部专家的标准

- 有AI辅助开发的实践经验(不是传统开发)
- 理解业务人员的限制
- 能写文档和培训(不只是干活)
- 长期合作意愿(不是一次性)

## 七、本系统的边界

### 本系统能保证的

✅ 代码符合基本规范
✅ 没有明显的安全漏洞
✅ 没有明显的bug
✅ 关键功能有自动化测试
✅ 生产事故能快速发现和回滚

### 本系统不能保证的

❌ 100% 没有bug(没有任何系统能保证)
❌ 业务逻辑完全正确(需要业务人员负责)
❌ 性能达到极致(需要专业优化)
❌ 通过严格的安全审计(需要专门服务)
❌ 应对所有未知场景(需要持续完善)

**质量保障是概率游戏,不是绝对保证**。本系统能让你们的质量水平**远超不用本系统的同等团队**,但不是免疫一切。
