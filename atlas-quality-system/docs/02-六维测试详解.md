# Atlas 质量保障系统：六维测试详解

> 本文档详细说明每个维度的测试机制、工具选型和实施细节

## 维度一：需求测试(Requirement Testing)

### 核心理念
**Garbage In, Garbage Out**——AI再聪明,如果输入需求不清晰,输出代码必然有缺陷。需求测试的目的是**在写代码前就把需求问清楚**。

### 实施机制

#### 1. 结构化需求模板
所有需求必须用 `templates/REQUIREMENT_TEMPLATE.md` 描述,强制包含：
- 业务目标
- 输入/输出规约
- 业务规则清单
- 异常场景列表
- 验收标准(可测试)
- 性能要求
- 安全要求

**反面教材**：
> "做一个用户登录功能"

**正确示范**：
> 用户登录功能(详见模板填写,必须包含：邮箱格式验证、密码长度6-20、连续3次失败锁定15分钟、记住我功能保持7天、登录成功跳转originalUrl或首页...)

#### 2. AI需求审查
使用 `prompts/01-需求澄清提示词.md`,让Claude反向审视需求,主动找出：
- 边界情况遗漏
- 异常场景未考虑
- 隐性假设
- 与现有功能的冲突
- 安全/性能隐患

#### 3. 验收标准前置(ATDD)
**写代码前**就用Gherkin格式定义验收标准：

```gherkin
Feature: 用户登录
  
  Scenario: 正常登录
    Given 用户已注册账号 "test@example.com" 密码 "Pass1234"
    When 用户输入正确凭证
    Then 应跳转到首页
    And 应显示欢迎信息
  
  Scenario: 密码错误锁定
    Given 用户已注册账号 "test@example.com"
    When 用户连续3次输入错误密码
    Then 账号应被锁定15分钟
    And 应显示"账号已锁定"提示
```

这些Gherkin场景**直接转化为E2E测试**,确保需求和测试1:1对应。

#### 4. 需求追溯矩阵

维护一个 `requirements-traceability.md` 文件：

| 需求ID | 需求描述 | 实现文件 | 测试文件 | 状态 |
|--------|---------|---------|---------|------|
| REQ-001 | 用户登录 | src/auth/login.ts | tests/auth/login.test.ts | ✅ |
| REQ-002 | 密码重置 | src/auth/reset.ts | tests/auth/reset.test.ts | ✅ |

每次需求变更时,自动检查所有相关测试是否也更新了。

### 工具选型

| 用途 | 工具 | 备注 |
|------|------|------|
| 需求文档管理 | Notion/Markdown文件 | 版本控制 |
| BDD测试框架 | Playwright + Cucumber | E2E场景 |
| 追溯工具 | 自定义脚本/CSV | 简单有效 |

### 业务人员日常操作

```
有新需求 
  ↓
1. 用《需求模板》写清楚
  ↓
2. 用《需求澄清提示词》让Claude审查
  ↓
3. 修改需求填补漏洞,直到Claude无新问题
  ↓
4. 把验收标准变成Gherkin场景
  ↓
5. 才能开始让Claude写代码
```

## 维度二：代码测试(Code Testing)

### 核心理念
代码测试不是"业务人员去看代码",而是**让机器和AI替业务人员审视代码**。

### 实施机制

#### 1. 静态分析(Static Analysis)
**自动检查代码质量,无需人工**：

**前端(TypeScript/React)**：
- **ESLint**：代码规范、潜在bug
- **TypeScript strict mode**：类型安全
- **Prettier**：自动格式化
- **stylelint**：CSS规范

**后端(根据技术栈)**：
- Python: `ruff`(快速Lint) + `mypy --strict`(类型) + `bandit`(安全)
- Node.js: `eslint` + `tsc --strict`
- 通用: SonarQube(代码气味、复杂度)

#### 2. 单元测试(Unit Testing)

**关键策略：让AI生成测试,但用变更测试验证测试质量**

业务人员流程：
```
1. AI生成功能代码
2. AI生成单元测试 (用《测试生成提示词》)
3. 运行测试,确认通过
4. 运行变更测试 (mutation testing)
5. 如果mutation score < 60%,要求AI改进测试
```

**变更测试的价值**：它会故意改坏代码(把 `>` 改成 `<` 等),如果测试还通过,说明测试是假的。

工具：
- 前端: `Stryker Mutator`
- 后端Python: `mutmut`
- 后端Node: `Stryker`

#### 3. 集成测试(Integration Testing)

测试模块间的协作。**这是最高ROI的测试层级,应作为主力。**

测试什么：
- API端点(请求-响应)
- 数据库交互(真实数据库,不用mock)
- 第三方服务集成(用Mock Server)

工具：
- API: Supertest(Node) / pytest+httpx(Python)
- 数据库: **Testcontainers**(关键!启动真实Postgres容器)
- Mock外部服务: WireMock / nock

#### 4. 契约测试(Contract Testing)

如果Atlas是前后端分离,前端和后端接口必须严格一致。

工具：
- **Pact**(消费者驱动契约)
- **Schemathesis**(从OpenAPI自动生成测试)

业务人员只需保证后端API有OpenAPI规范文件,工具会自动测试所有端点的边界情况。

#### 5. 安全扫描(Security Testing)

**这是业务人员场景下最重要的一类测试**——AI很容易生成有安全漏洞的代码。

必须配置的扫描：
- **SAST(静态应用安全测试)**：CodeQL / Semgrep
- **依赖漏洞扫描**：Snyk / Dependabot / `npm audit` / `pip-audit`
- **密钥泄露扫描**：TruffleHog / detect-secrets / gitleaks
- **DAST(动态安全测试)**：OWASP ZAP(对Staging环境扫描)
- **容器扫描**：Trivy(扫描Docker镜像)

#### 6. AI Code Review(关键创新)

**这是你们场景下的核心机制**——让Claude审查Claude生成的代码。

实现方式：每次PR触发自动调用Claude API,使用专门的Code Review提示词,严格检查：
- 安全性(SQL注入、XSS、CSRF等)
- 业务逻辑正确性
- 边界情况处理
- 错误处理完整性
- 性能问题(N+1查询、内存泄漏)
- 是否遵守CLAUDE.md规范

如果发现严重问题,自动阻断PR合并。

详细配置见 `ci-config/.github-workflows-quality-gate.yml`。

### 覆盖率要求

| 代码区域 | 行覆盖率 | 分支覆盖率 | Mutation Score |
|---------|---------|-----------|----------------|
| 核心业务逻辑 | ≥85% | ≥80% | ≥70% |
| 工具函数 | ≥90% | ≥85% | ≥75% |
| API端点 | ≥80% | ≥75% | ≥60% |
| UI组件 | ≥70% | ≥60% | - |
| 整体 | ≥75% | ≥70% | ≥60% |

## 维度三:架构测试(Architecture Testing)

### 核心理念
**架构是代码的骨架。骨架歪了,后期改的成本是最初设计的100倍。**

业务人员让AI写代码时,AI每次都"重新设计",很容易导致架构混乱。架构测试就是**用机器强制约束AI的设计自由度**。

### 实施机制

#### 1. 架构适应度函数(Architectural Fitness Functions)

将架构约束写成可执行的测试。例如：

**前端约束示例**(用 `dependency-cruiser`)：
```yaml
# 业务组件不能直接调用API,必须通过service层
forbidden:
  - name: "components不能直接调用API"
    from: { path: "^src/components" }
    to: { path: "^src/api" }
    severity: error
```

**后端约束示例**(用 `archunit-ts` 或自定义规则)：
```typescript
// Controller不能直接调用Repository,必须通过Service
test('Controllers只能依赖Services', () => {
  const violations = findViolations(
    fromPackage: 'controllers',
    forbiddenDependency: 'repositories'
  );
  expect(violations).toEqual([]);
});
```

#### 2. 依赖关系可视化

工具：`dependency-cruiser`(JS/TS) / `pydeps`(Python)

每次CI生成依赖图,自动检测：
- 循环依赖(致命问题)
- 跨层依赖(违反架构)
- 孤立模块(死代码)

#### 3. 数据库变更管控

**这是业务人员场景下最危险的领域。**

强制规则：
- 所有数据库schema变更必须通过Migration(Alembic/Knex/Prisma Migrate)
- Migration必须有 `up` 和 `down`(可回滚)
- Migration在CI中自动测试(应用→回滚→再应用)
- 生产应用账号无DDL权限(防止AI误改表结构)

#### 4. API版本管控

约定:
- API路径包含版本号 `/api/v1/...`
- 已发布API的修改必须保持向后兼容
- 破坏性变更必须发新版本
- 用OpenAPI规范+Schema diff工具检测breaking change

#### 5. 第三方依赖治理

每次新增npm/pip包必须经过：
- 自动扫描:许可证、漏洞、维护状态
- 人工审批:CODEOWNERS规则要求依赖文件变更必须人审

工具：
- `license-checker`(JS) / `pip-licenses`(Python):许可证审查
- Snyk / Dependabot:漏洞监控
- `is-website-vulnerable`:运行时检查

### 业务人员日常操作

涉及以下场景时,**必须**使用 `prompts/06-架构守护提示词.md`：
- 新增数据库表/字段
- 新增第三方依赖
- 修改文件目录结构
- 新增/修改API端点
- 修改部署配置

## 维度四:界面测试(UI Testing)

### 核心理念
**用户看到什么,直接决定他对软件的判断。**

UI测试不是测"功能能不能用",而是测"看起来对不对、用起来流畅不流畅"。

### 实施机制

#### 1. 组件测试(Component Testing)

测试单个UI组件的行为,介于单元测试和E2E之间。

工具：**Playwright Component Testing** 或 **Cypress Component**

测试什么：
- Props变化时渲染正确
- 用户交互(点击、输入)行为正确
- 异步加载状态(loading/error/success)
- 边界数据(空、超长、特殊字符)

#### 2. 视觉回归测试(Visual Regression)

**自动截图比对,发现CSS bug。**

工具选型：
- **Chromatic**(Storybook集成,推荐)
- **Percy**(BrowserStack)
- **Playwright自带截图比对**(免费方案)

工作流：
```
PR提交 → 自动渲染所有页面/组件 → 截图 → 与基线比对
  ↓
如有视觉差异 → 标记PR需要人工确认
  ↓
确认是预期变化 → 更新基线
确认是bug → 修复
```

#### 3. 可访问性测试(Accessibility / A11y)

**法律要求 + 用户体验**。AI生成的UI经常忽略可访问性。

工具：
- **axe-core**(集成到Playwright)
- **Lighthouse CI**(自动化Lighthouse评分)
- **Pa11y**(命令行工具)

强制要求：
- WCAG 2.1 AA合规
- Lighthouse Accessibility评分 ≥ 90
- 所有交互元素有aria-label
- 颜色对比度 ≥ 4.5:1

#### 4. 跨浏览器测试

测试矩阵：

| 浏览器 | 优先级 | 工具 |
|-------|-------|------|
| Chrome 最新版 | P0 | Playwright |
| Firefox 最新版 | P1 | Playwright |
| Safari 最新版 | P1 | Playwright |
| Edge 最新版 | P2 | Playwright |
| iOS Safari | P1 | BrowserStack |
| Android Chrome | P1 | BrowserStack |

#### 5. 响应式测试

测试断点：
- 手机:375px(iPhone SE)
- 平板:768px(iPad)
- 桌面:1280px(常见笔记本)
- 大屏:1920px

每个关键页面在每个断点都要截图比对。

#### 6. 国际化测试

如果Atlas支持多语言：
- 所有文案必须从语言文件加载,禁止硬编码
- 测试长文本溢出(德语通常最长)
- 测试RTL语言(阿拉伯语、希伯来语)
- 测试日期/数字/货币格式

### 业务人员日常操作

```
UI变更后:
  ↓
1. 提交PR
  ↓
2. 等待视觉回归报告(自动)
  ↓
3. 检查截图差异:
   - 是预期变化 → 在Chromatic/Percy点"Accept"
   - 是意外变化 → 让Claude修复
  ↓
4. 检查Lighthouse报告(自动评分)
   - Performance ≥ 80
   - Accessibility ≥ 90
   - Best Practices ≥ 90
   - SEO ≥ 90
  ↓
5. 全部通过才能合并
```

## 维度五:交互测试(Interaction Testing)

### 核心理念
功能能用 ≠ 用得舒服。交互测试关注**完整用户操作链路的流畅性**。

### 实施机制

#### 1. 端到端测试(E2E Testing)

模拟真实用户操作,从打开浏览器到完成任务。

工具：**Playwright**(强烈推荐,优于Cypress和Selenium)

测试什么：
- 关键用户路径(Top 10必须100%覆盖)
- 跨页面流程(登录→搜索→下单→支付→确认)
- 多角色场景(管理员vs普通用户)

**Page Object Model实践**：

```typescript
// pages/LoginPage.ts
export class LoginPage {
  constructor(private page: Page) {}
  
  async login(email: string, password: string) {
    await this.page.fill('[data-testid=email]', email);
    await this.page.fill('[data-testid=password]', password);
    await this.page.click('[data-testid=login-btn]');
  }
}

// tests/login.spec.ts
test('用户成功登录后跳转首页', async ({ page }) => {
  const loginPage = new LoginPage(page);
  await page.goto('/login');
  await loginPage.login('test@example.com', 'Pass1234');
  await expect(page).toHaveURL('/dashboard');
});
```

业务人员让Claude生成E2E测试时,必须指定使用Page Object Model。

#### 2. 性能测试(Performance Testing)

**前端性能预算**：

| 指标 | 目标 | 测量工具 |
|------|------|---------|
| First Contentful Paint | < 1.8s | Lighthouse |
| Largest Contentful Paint | < 2.5s | Lighthouse |
| Time to Interactive | < 3.8s | Lighthouse |
| Cumulative Layout Shift | < 0.1 | Lighthouse |
| First Input Delay | < 100ms | Real User Monitoring |
| Bundle大小 | < 250KB(gzip) | webpack-bundle-analyzer |

**后端性能预算**：

| 指标 | 目标 | 测量工具 |
|------|------|---------|
| API响应P95 | < 200ms | k6 / artillery |
| API响应P99 | < 500ms | k6 / artillery |
| 数据库查询P95 | < 50ms | pg_stat / APM |
| 错误率 | < 0.1% | Sentry / DataDog |

CI中运行 `k6` 或 `artillery` 做压测,任何关键API性能下降超过20%自动失败。

#### 3. 表单交互测试

表单是bug高发区。每个表单必须测试：
- 必填字段验证
- 格式验证(邮箱、电话、日期)
- 最大长度截断
- 特殊字符处理(SQL注入、XSS attempt)
- 提交时的loading状态
- 提交失败的错误处理
- 提交成功的反馈
- 重复提交防护(防止双击下单)

#### 4. 错误恢复测试

模拟异常环境：
- 网络中断(用Playwright的 `route` 拦截)
- 慢网(模拟3G)
- 服务器500错误
- 超时
- 浏览器刷新(状态保持)
- 浏览器后退(URL正确)

#### 5. 键盘导航测试

确保所有功能可以用键盘完成:
- Tab键焦点顺序合理
- Enter/Space触发按钮
- ESC关闭弹窗
- 快捷键(如有)

### 关键路径覆盖

业务人员必须列出"用户Top 10关键路径",并100%自动化测试。例如(假设Atlas是某种业务系统)：

| 路径ID | 描述 | 频率 | 自动化状态 |
|--------|------|------|-----------|
| P-001 | 用户注册→登录→首次使用 | 高 | ✅ |
| P-002 | 创建新项目→邀请成员 | 高 | ✅ |
| P-003 | 数据导入→处理→导出 | 高 | ✅ |
| ... | ... | ... | ... |

## 维度六:场景测试(Scenario Testing)

### 核心理念
**实验室能跑通,生产不一定能跑通。**

场景测试不是补充,而是**最重要的最终验证**——它让测试接触到真实的复杂性。

### 实施机制

#### 1. 用户旅程测试(User Journey)

不测单个功能,测**完整故事**：

```
"小张是新员工,他需要在系统中:
1. 用公司邮箱注册
2. 完成入职引导
3. 加入'市场部'团队
4. 申请权限审批
5. 完成第一个任务并提交
6. 收到主管反馈
7. 标记任务完成"
```

这个完整流程作为一个E2E测试,**任何一步失败整个测试失败**。

#### 2. 影子流量(Shadow Traffic)

**生产环境上线后**,把真实流量复制一份发到Staging,验证新版本与旧版本的输出一致性。

工具：**GoReplay**(开源,简单有效)

价值:
- 发现"测试环境构造不出来"的bug
- 验证性能在真实负载下的表现
- 不影响真实用户

#### 3. 灰度发布观察

新版本不直接全量,先给1%用户用,监控关键指标：
- 错误率是否上升
- P95响应时间是否变慢
- 业务指标(转化率、留存)是否异常

工具：
- **Argo Rollouts**(K8s环境)
- **Flagger**
- **Vercel/Netlify**自带的预览部署

#### 4. 异常场景测试

主动构造异常环境,验证系统韧性：

**网络异常**：
- 50%丢包率下系统是否可用
- 高延迟(2秒+)下UI是否友好
- 离线状态下是否有合理提示

**数据异常**：
- 数据库中有脏数据(NULL、超长字符串、特殊编码)
- 时区不一致
- 并发修改同一记录

**负载异常**：
- 1000并发用户同时操作
- 单用户每秒发100次请求

**外部依赖异常**：
- 第三方API超时
- 第三方API返回错误数据
- 第三方API完全宕机

工具：
- **Chaos Mesh**(K8s环境混沌工程)
- **Toxiproxy**(网络故障注入)
- **Locust** / **k6**(负载测试)

#### 5. 探索性测试自动化

**让AI主动找bug**：

工具：
- **Monkey Testing**:随机点击/输入,看会不会崩溃
- **Fuzzing**:用海量随机数据轰炸API
- **基于属性的测试**(已在代码维度提到):描述属性而非具体输入

**实践**:让Claude定期生成"破坏性测试用例",特别针对：
- 边界值(0, -1, MAX_INT, NaN)
- 特殊字符串(emoji, Unicode, 控制字符)
- 时间边界(1970, 2038, 闰年)
- 并发场景

#### 6. 真实用户监控(RUM)

**这是上线后的"持续测试"**。

工具：
- **Sentry**:错误追踪 + 性能监控
- **Datadog RUM**:用户会话回放
- **LogRocket**:用户行为录制

收集真实用户的:
- JS错误
- 页面性能
- 用户操作路径
- 转化漏斗

每周由"AI代码守护者"review,把发现的问题转化为新的测试用例,**持续完善测试覆盖**。

### 业务人员日常操作

```
新功能上线前:
  ↓
1. 列出该功能的真实使用场景(至少5个)
  ↓
2. 每个场景写成E2E测试(用《测试生成提示词》)
  ↓
3. 上Staging跑完整测试
  ↓
4. 灰度发布到生产(1% → 10% → 50% → 100%)
  ↓
5. 每个阶段观察Sentry/监控指标
  ↓
6. 任何异常立即回滚,不要硬扛
```
