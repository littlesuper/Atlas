# Atlas 质量保障系统:日常工作流程

> 这份文档告诉业务人员**每天具体怎么操作**

## 一、每个新需求的标准流程

```
有新需求
   ↓
【第1步】需求结构化     → 用模板填写
   ↓
【第2步】需求审查        → AI找漏洞
   ↓
【第3步】定义验收标准    → 写Gherkin场景
   ↓
【第4步】生成代码        → AI写实现
   ↓
【第5步】生成测试        → AI写测试
   ↓
【第6步】AI自审          → AI Review代码
   ↓
【第7步】本地验证        → 跑pre-commit + 测试
   ↓
【第8步】提交PR          → 等待CI检查
   ↓
【第9步】处理CI反馈      → 修复问题
   ↓
【第10步】等待人审       → 关键改动
   ↓
【第11步】合并部署       → 自动到Staging
   ↓
【第12步】Staging验证   → 真实环境测试
   ↓
【第13步】灰度发布      → 1% → 10% → 50% → 100%
   ↓
【第14步】监控观察      → 24小时关键指标
```

下面详细说明每一步。

---

## 第1步:需求结构化

### 操作步骤

1. 复制 `templates/REQUIREMENT_TEMPLATE.md` 内容
2. 填写所有字段(不允许留空)
3. 保存为 `docs/requirements/REQ-XXX-需求名称.md`

### 输出物
一份结构化的需求文档,包含:
- 业务目标
- 输入输出规约
- 业务规则
- 异常场景
- 验收标准
- 性能/安全要求

### 不要做什么

❌ **不要直接对Claude说**:"做一个用户管理功能"
❌ **不要省略异常场景**:"出错的情况以后再说"
❌ **不要假设Claude懂你**:它不知道你们公司的业务

---

## 第2步:需求审查

### 操作步骤

1. 打开新的Claude对话
2. 把整个需求文档贴进去
3. 然后贴 `prompts/01-需求澄清提示词.md` 的内容
4. Claude会列出潜在问题清单
5. 针对每个问题,要么完善需求,要么说明"已考虑,理由是..."
6. 重复直到Claude没有新问题

### 示例对话

```
你: [贴需求文档]
你: [贴需求澄清提示词]

Claude: 我审查了需求,发现以下问题:
  1. 密码强度规则未说明,建议明确...
  2. 用户已注册同邮箱时如何处理?
  3. 注册后是否需要邮箱验证?
  ...

你: 1. 密码至少8位,需含字母数字
   2. 提示"邮箱已被使用"
   3. 需要,24小时内有效
   [回到第1步,更新需求文档]

你: [再次贴更新后的需求] [再贴提示词]

Claude: 还有以下问题:
  ...
```

直到Claude说"没有发现明显遗漏"。

---

## 第3步:定义验收标准

### 操作步骤

把需求中的每条验收点转化为Gherkin格式:

```gherkin
Feature: [功能名]

  Scenario: [场景描述]
    Given [前置条件]
    When [用户操作]
    Then [预期结果]
    And [其他验证]
```

### 示例

需求:"用户登录,密码错误时锁定"

Gherkin:
```gherkin
Feature: 用户登录安全

  Scenario: 密码连续错误锁定
    Given 用户 "test@example.com" 已注册
    When 用户连续3次输入错误密码
    Then 账号被锁定15分钟
    And 显示提示 "账号已锁定,请15分钟后再试"
    And 此时输入正确密码也无法登录

  Scenario: 锁定时间过后恢复
    Given 用户账号已锁定15分钟
    When 等待16分钟后用正确密码登录
    Then 登录成功
```

### 验证

让Claude检查Gherkin是否覆盖了所有需求条款:

```
你: [贴需求] [贴Gherkin]
   请检查这些Gherkin场景是否覆盖了需求中的所有验收标准,有遗漏的请补充。
```

---

## 第4步:生成代码

### 操作步骤

1. 打开新的Claude对话
2. 第一条消息:把项目的 `CLAUDE.md` 内容完整贴入
3. 第二条消息:把需求文档 + Gherkin场景贴入
4. 第三条消息:贴 `prompts/02-代码生成提示词.md`
5. Claude生成代码
6. 把代码保存到正确的目录

### 关键提醒

⚠️ **每次新对话都要重新贴CLAUDE.md**,因为Claude没有项目记忆
⚠️ **不要让Claude"猜"你的技术栈**,CLAUDE.md里写明确
⚠️ **复杂功能分多步**,不要一次让AI生成几百行

### 推荐做法:增量生成

不要一次说"做一个完整的用户系统",而是:

```
第一轮: 先做用户数据模型(database schema + entity)
  ↓ 验证通过
第二轮: 做注册API
  ↓ 验证通过
第三轮: 做登录API
  ↓ 验证通过
第四轮: 做密码重置
...
```

每一轮都验证完再进入下一轮。

---

## 第5步:生成测试

### 操作步骤

1. 在同一个Claude对话中(让它有上下文)
2. 贴 `prompts/04-测试生成提示词.md`
3. Claude生成测试代码
4. 保存到对应的test目录

### 测试覆盖要求

让Claude生成至少包括:
- ✅ 正常路径(happy path)
- ✅ 每个异常场景
- ✅ 边界值(空、零、负数、超大、特殊字符)
- ✅ 错误处理路径
- ✅ 验证Gherkin中的每个场景

### 验证测试质量

测试写完后,运行变更测试:

```bash
# 后端Python
mutmut run --paths-to-mutate src/

# 前端
npx stryker run

# 查看结果,如果mutation score < 60%
# 让Claude补充测试
```

---

## 第6步:AI Code Review

### 操作步骤

1. **打开新的Claude对话**(关键!不要在生成代码的对话里review)
2. 贴 `prompts/03-代码审查提示词.md`
3. 贴需要审查的代码
4. Claude给出严格的审查报告
5. 根据报告修复问题

### 为什么用新对话?

**生成代码的Claude会"为自己辩护"**,新对话的Claude没有这个偏见,更挑剔。

这是双AI互审的核心机制。

### 审查标准

新对话的Claude会按以下清单严格检查:

- 🔴 **安全性**(零容忍)
  - SQL注入、XSS、CSRF
  - 硬编码密钥
  - 输入验证缺失
  - 越权访问

- 🟠 **正确性**
  - 边界情况
  - 并发安全
  - 错误处理
  - 事务完整性

- 🟡 **可维护性**
  - 命名清晰
  - 复杂度可控
  - 符合规范

如果出现🔴问题,**必须修复才能继续**。

---

## 第7步:本地验证

### 操作步骤

```bash
# 1. 安装依赖(只需要一次)
git clone <atlas-repo>
cd atlas
npm install  # 或 pip install -r requirements.txt

# 2. 安装pre-commit hooks(只需要一次)
pre-commit install

# 3. 添加修改的文件
git add .

# 4. 尝试提交(会自动运行检查)
git commit -m "feat: 添加用户登录功能"
```

如果pre-commit检查失败:
- 看错误信息
- 把错误信息+代码贴给Claude,让它修复
- 重新提交

### 常见pre-commit错误

| 错误类型 | 含义 | 解决方法 |
|---------|------|---------|
| trailing-whitespace | 行尾有空格 | 自动修复,重新git add |
| detect-secrets | 发现疑似密钥 | 移除密钥,用环境变量 |
| ruff/eslint | 代码风格问题 | 自动修复,重新git add |
| mypy/tsc | 类型错误 | 让Claude修复 |
| bandit | 安全问题 | 让Claude修复 |
| pytest | 测试失败 | 修复测试或代码 |

---

## 第8步:提交PR

### 操作步骤

```bash
# 1. 推送到分支
git push origin feat/user-login

# 2. 在GitHub上创建PR
# 3. PR描述使用模板(自动)
# 4. 等待CI检查(约5-15分钟)
```

### PR描述模板

```markdown
## 关联需求
REQ-XXX: [需求描述]

## 变更内容
- 新增 用户登录API
- 新增 登录页面UI
- 新增 17个单元测试 + 5个E2E场景

## 验收标准对照
- [x] 正常登录跳转首页
- [x] 密码错误3次锁定
- [x] 锁定15分钟后恢复

## 测试报告
- 单元测试覆盖率: 87%
- Mutation Score: 65%
- E2E测试: 全部通过
- Lighthouse Performance: 92

## 风险评估
- 影响范围: 仅登录模块
- 数据库变更: 无
- 依赖变更: 无
```

## 第9步:处理CI反馈

CI会自动跑20+项检查,任何一项失败都会标红。

### 失败处理流程

```
看CI日志
  ↓
确定哪个检查失败
  ↓
用《Bug诊断提示词》让Claude分析
  ↓
按Claude建议修复
  ↓
重新push,触发CI重新跑
```

### 不要做什么

❌ **不要绕过失败的检查**(虽然有时候manager会想这样做)
❌ **不要标记测试为skip**(除非真的不再需要)
❌ **不要用 `--no-verify` 跳过pre-commit**

如果某个检查"误报",联系AI代码守护者评估,不要自己决定。

---

## 第10步:等待人审

### CODEOWNERS自动指派

某些类型的变更会自动指派给"AI代码守护者"或其他角色审查:

| 变更内容 | 自动指派给 |
|---------|-----------|
| 数据库migration | DBA / 守护者 |
| 认证/授权代码 | 安全负责人 / 守护者 |
| CI/CD配置 | DevOps / 守护者 |
| 第三方依赖 | 守护者 |
| 支付相关 | 高级开发者 / 守护者 |

### 业务人员配合事项

被指派审查后:
- 主动通知审查者(Slack/钉钉/邮件)
- 准备好回答问题
- 接受修改建议,不要"硬刚"
- 修改后重新push,会自动通知再审

---

## 第11步:合并部署

CI全绿 + 人审通过后,可以合并:

```
点 "Merge pull request" 按钮
  ↓
自动触发部署到Staging环境
  ↓
等待5-10分钟,部署完成
  ↓
收到Slack通知"部署成功"
```

---

## 第12步:Staging验证

### 自动化验证(已自动运行)

- 冒烟测试(关键功能能跑)
- 完整E2E测试套件
- 性能基准测试
- 安全扫描

### 手动验证(业务人员做)

虽然有自动化,**核心场景仍要人工走一遍**:

```
打开Staging URL
  ↓
按以下清单操作:
  □ 你刚做的功能,完整走一遍正常路径
  □ 故意触发一个错误场景,看错误处理
  □ 在不同设备/浏览器看一下UI
  □ 检查是否有控制台错误(F12打开)
  ↓
都OK → 进入下一步
有问题 → 立即记录Bug,回到开发
```

---

## 第13步:灰度发布

### 发布流程

业务人员**不直接控制生产部署**,需要由"AI代码守护者"或"产品负责人"批准:

```
Staging验证通过
  ↓
申请发布(填发布单)
  ↓
负责人批准
  ↓
自动开始Canary发布:
  ├─ 1% 流量 (观察1小时)
  ├─ 10% 流量 (观察4小时)
  ├─ 50% 流量 (观察12小时)
  └─ 100% 流量
  ↓
任何阶段指标异常 → 自动回滚
```

### 关键指标观察

每个阶段必须监控:

| 指标 | 阈值 | 工具 |
|------|------|------|
| 错误率 | < 0.5% | Sentry |
| P95响应时间 | < 增加20% | Datadog |
| 5xx错误数 | 不超过基线1.5倍 | Datadog |
| 业务指标 | 不显著下降 | 业务监控 |

---

## 第14步:监控观察

发布完成后**24小时内不要松懈**:

- 每小时看一眼Sentry
- 注意用户反馈渠道
- 准备随时回滚

### 出现问题怎么办?

**优先级1:立即回滚**
不要尝试"在生产环境修复",回滚是最快的止血。

```bash
# 一键回滚到上一版本
gh workflow run rollback.yml
```

**优先级2:分析原因**
回滚后冷静分析,使用《Bug诊断提示词》。

**优先级3:复盘改进**
按 `checklists/生产事故应急清单.md` 操作,把这次事故变成新的测试用例。

## 二、其他常见任务流程

### 修Bug流程

```
收到Bug报告
  ↓
1. 用《Bug报告模板》记录
  ↓
2. 用《Bug诊断提示词》让Claude分析根因
  ↓
3. 先写一个失败的测试(复现Bug)
  ↓
4. 再修代码让测试通过
  ↓
5. 后续步骤同正常需求(从第6步开始)
```

**关键原则:先写测试再修代码**——这能保证Bug不会再次出现。

### 重构流程

⚠️ **重构是高风险操作,务必小心**

```
1. 确认现有测试覆盖率 > 80%
   (如果不够,先补测试再重构)
  ↓
2. 写明重构目标(为什么重构,改什么)
  ↓
3. 让Claude分小步重构,每步都跑测试
  ↓
4. 每步重构后跑完整测试套件
  ↓
5. 任何测试失败立即停止,分析原因
```

### 添加新依赖流程

```
1. 评估必要性:为什么需要这个依赖?
  ↓
2. 调研:许可证、维护状态、漏洞历史
  ↓
3. 找AI代码守护者审批
  ↓
4. 批准后添加,提交PR
  ↓
5. CI自动检查依赖安全性
```

## 三、每日工作节奏建议

### 每天

- 早上: 看一眼Sentry是否有新错误
- 工作时: 严格按本流程做需求
- 下班前: 提交当天工作,确保CI绿

### 每周

- 周一: 看上周CI拦截了什么
- 周五: 回顾本周质量指标

### 每月

- 月初: 月度质量审计(用清单)
- 月末: 更新CLAUDE.md(新发现的规范)

## 四、心态建设

### 不要

❌ "这是小改动,不用走流程"
→ 没有"小改动",所有变更必须走完整流程

❌ "测试通过了,应该没问题"
→ 测试只能证明"测到的没问题",场景永远比测试多

❌ "Claude说没问题,那就上吧"
→ Claude会犯错,机制和流程才是保障

❌ "出问题再修就行了"
→ 生产事故的成本是开发期发现的100倍

### 要

✅ "宁可CI失败10次,不要生产挂1次"
✅ "完整流程比快速上线重要"
✅ "每次发现问题,都是改进体系的机会"
✅ "我不懂代码没关系,但我懂业务和流程"

```

```
