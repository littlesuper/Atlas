# Atlas 质量保障系统：总体方案

## 一、为什么需要这套体系？

### 你们的真实风险

业务人员通过AI写代码上生产,面临的风险**与传统开发完全不同**：

| 风险类型 | 传统开发 | 你们的场景 | 危险等级 |
|---------|---------|-----------|---------|
| 代码bug | 开发者能识别 | **业务人员无法识别** | 🔴 致命 |
| 安全漏洞 | 有意识 | **几乎零意识** | 🔴 致命 |
| AI幻觉 | 不存在 | **频繁出现** | 🔴 致命 |
| 架构腐化 | 有Code Review | **无人把关** | 🟠 高 |
| 隐性需求缺失 | 经验弥补 | **只想正常路径** | 🟠 高 |
| 生产事故响应 | 能调试 | **不会调试** | 🟠 高 |

### 核心策略：四道防线

```
业务人员 + AI
     ↓
┌─────────────────────────────────────┐
│ 防线1: 输入控制                       │
│   - CLAUDE.md项目宪法                 │
│   - 标准化需求模板                    │
│   - 提示词模板库                      │
│   → 让AI在正确的轨道上工作            │
└─────────────────────────────────────┘
     ↓
┌─────────────────────────────────────┐
│ 防线2: 自动化质量门禁                 │
│   - Pre-commit本地检查                │
│   - CI/CD多层扫描                    │
│   - AI审查AI生成的代码               │
│   - 自动测试生成与执行               │
│   → 机器替业务人员把关               │
└─────────────────────────────────────┘
     ↓
┌─────────────────────────────────────┐
│ 防线3: 强制人工把关                   │
│   - CODEOWNERS自动指派               │
│   - 关键变更必须人审                  │
│   - AI代码守护者每周巡检             │
│   → 关键决策有懂代码的人参与         │
└─────────────────────────────────────┘
     ↓
┌─────────────────────────────────────┐
│ 防线4: 生产环境保护                   │
│   - Feature Flags特性开关            │
│   - 渐进式发布(Canary)              │
│   - 全方位监控告警                    │
│   - 数据库权限隔离                    │
│   → 即使有bug也限制爆炸半径          │
└─────────────────────────────────────┘
     ↓
   生产环境
```

## 二、六维测试体系总览

针对"代码、架构、需求、界面、交互、用户场景"六个维度,每个维度都有专门的测试机制：

### 维度1：需求维度(Requirement)

**目标**：保证软件做了"该做的事"

**核心机制**：
- 需求模板强制结构化(避免AI胡乱发挥)
- 验收标准前置定义(写代码前就明确)
- AI辅助需求审查(发现遗漏的边界场景)
- 需求-代码-测试三方追溯

**业务人员要做的**：
- 用《需求模板》写清需求
- 用《需求澄清提示词》让AI找出需求漏洞

### 维度2：代码维度(Code)

**目标**：保证代码"做对了事"

**核心机制**：
- 静态分析(Lint、类型检查)
- 单元测试(AI自动生成+变更测试验证)
- 安全扫描(SAST、密钥扫描、依赖漏洞)
- AI Code Review(双AI互审)
- 复杂度检查(防止AI过度设计)
- 重复代码检测(AI每次重写导致重复)

**业务人员要做的**：
- 提交代码前运行 `pre-commit`
- 每个PR等待CI全绿
- 用《代码审查提示词》让AI自审

### 维度3：架构维度(Architecture)

**目标**：保证系统"以正确方式构造"

**核心机制**：
- 架构适应度函数(强制约束)
- 依赖关系可视化(防止环依赖)
- API契约测试(模块间接口稳定)
- 数据库迁移强制审查
- 第三方依赖治理

**业务人员要做的**：
- 任何架构变动必须用《架构守护提示词》
- 新增依赖必须经过审批
- 数据库变更必须走Migration

### 维度4：界面维度(UI)

**目标**：保证用户"看到的是对的"

**核心机制**：
- 组件级测试(隔离的UI单元)
- 视觉回归测试(自动截图比对)
- 可访问性测试(WCAG合规)
- 跨浏览器测试(Chrome/Firefox/Safari)
- 响应式设计测试(PC/平板/手机)
- 国际化测试(多语言、RTL)

**业务人员要做的**：
- 提交UI变更后等待视觉回归报告
- 检查Lighthouse评分

### 维度5：交互维度(Interaction)

**目标**：保证用户"操作流畅,体验良好"

**核心机制**：
- E2E测试(模拟真实用户操作)
- 性能测试(页面加载<3s,交互<100ms)
- 表单测试(各种输入边界)
- 错误恢复测试(网络中断、刷新)
- 无障碍交互(键盘导航、屏幕阅读器)

**业务人员要做的**：
- 用《测试生成提示词》让AI生成E2E场景
- 真实用户路径必须100%覆盖

### 维度6：场景维度(Scenario)

**目标**：保证软件"在真实使用中可用"

**核心机制**：
- 用户旅程测试(端到端故事)
- 影子流量(生产数据回放)
- 灰度发布观察(真实用户验证)
- 异常场景测试(网络差、并发高、数据脏)
- 探索性测试自动化(Monkey Test)

**业务人员要做的**：
- 列出用户Top 10关键路径并100%自动化
- 上线后监控关键指标
- 收集用户反馈并转化为新测试用例

## 三、测试金字塔(适配你们的场景)

```
                ┌─────────────┐
                │  E2E (10%)  │  ← 关键用户路径
                ├─────────────┤
                │ 集成测试(50%) │  ← 主力测试,最高ROI
                ├─────────────┤
                │ 单元测试(30%) │  ← 核心算法/业务规则
                ├─────────────┤
                │ 静态检查(10%) │  ← Lint/类型/安全
                └─────────────┘
```

**为什么集成测试是主力？**
- 业务人员看不懂代码细节,纯单元测试容易"测了寂寞"
- 集成测试更接近真实业务行为,价值更高
- AI生成的代码经常有"看似正确但接口对不上"的问题,集成测试能抓住

## 四、自动化质量门禁的工作机制

每次代码变更,都会经过这条流水线：

```
开发者本地:
  git commit → [pre-commit hooks自动运行]
    ├── 代码格式化 (black/prettier)
    ├── Lint检查 (ruff/eslint)
    ├── 类型检查 (mypy/typescript)
    ├── 密钥扫描 (detect-secrets)
    └── 单元测试 (快速版)
  ↓ 全部通过才能提交
  
git push → [GitHub Actions CI触发]
    ├── 🔒 安全扫描
    │   ├── CodeQL代码安全分析
    │   ├── Snyk依赖漏洞扫描
    │   ├── Bandit/ESLint安全规则
    │   └── TruffleHog密钥扫描
    │
    ├── 📊 静态分析
    │   ├── 完整Lint
    │   ├── 严格类型检查
    │   ├── 圈复杂度检查
    │   └── 重复代码检测
    │
    ├── 🧪 测试套件
    │   ├── 单元测试 (覆盖率≥70%)
    │   ├── 集成测试
    │   ├── 契约测试
    │   └── 变更测试 (Mutation Score≥60%)
    │
    ├── 🤖 AI Code Review
    │   ├── 安全性检查
    │   ├── 业务逻辑检查
    │   ├── 边界情况检查
    │   └── 规范合规检查
    │
    ├── 🎨 UI测试
    │   ├── 组件测试
    │   ├── 视觉回归
    │   └── 可访问性
    │
    └── 🌐 E2E测试
        └── 关键用户路径
  ↓ 全部通过才能合并
  
合并到main → [自动部署到Staging]
    ├── 冒烟测试
    ├── 完整E2E测试
    ├── 性能基准测试
    └── 数据库迁移验证
  ↓ 验证通过
  
[手动批准] → 部署到生产 (Canary)
    ├── 1% 流量观察 (1小时)
    ├── 10% 流量观察 (4小时)
    ├── 50% 流量观察 (12小时)
    └── 100% 全量
```

**关键原则**：**任何一步失败,流程立即停止**。

## 五、组织与角色

### 必须的角色配置

| 角色 | 谁来担任 | 职责 |
|------|---------|------|
| **业务开发** | 业务人员们 | 用AI写代码,执行流程 |
| **AI代码守护者** | 部门最懂技术的人(可兼职) | 处理CI报警、维护规范、月度审计 |
| **产品负责人** | 业务负责人 | 定义需求、验收成果 |
| **运维支持** | 外部支持(可外包) | 处理基础设施和生产事故 |

### AI代码守护者的关键职责

这个人**绝不可缺**,他/她每周需要花4-8小时做：

1. **每周CI报告review**：检查门禁拦截了什么、有什么趋势
2. **关键PR人工审查**：CODEOWNERS指派的PR
3. **CLAUDE.md维护**：根据新发现的问题更新规范
4. **生产监控审查**：每周看一次Sentry/告警趋势
5. **业务人员答疑**：处理AI解决不了的问题
6. **月度质量审计**：使用《月度质量审计清单》

如果暂时找不到这个人,**建议外包给专业咨询团队或暂缓上生产**。

## 六、度量与持续改进

### 必须跟踪的指标

| 指标 | 健康值 | 危险信号 | 数据来源 |
|------|--------|---------|---------|
| 生产缺陷逃逸率 | < 1个/月 | 上升 | Sentry |
| CI拦截率 | 10-30% | <5%或>50% | GitHub Actions |
| 测试覆盖率 | > 70% | 下降 | Codecov |
| 变更测试得分 | > 60% | 下降 | Mutation测试 |
| 平均故障恢复时间 | < 30min | 延长 | 事故记录 |
| 部署频率 | 每周>3次 | 下降 | CI记录 |
| Flaky测试比例 | < 5% | > 10% | CI报告 |
| 安全告警数 | 0 high+ | 任何高危 | Snyk/CodeQL |

### 持续改进循环

```
每周一:    审查上周CI拦截、生产告警
每周五:    AI代码守护者总结报告
每月1日:   月度质量审计 + CLAUDE.md更新
每季度:    灾难恢复演练 + 工具链评估
```

## 八、常见误区警告

### ❌ 误区1：「先快速做出来,质量后面再说」
**后果**：技术债务雪球,最终重写。
**正确做法**：从第一行代码就嵌入质量机制。

### ❌ 误区2：「我们不懂代码,所以测试做不了」
**后果**：质量保障空白。
**正确做法**：本体系**不需要业务人员懂代码**,一切自动化。

### ❌ 误区3：「Claude生成的代码看起来挺好,应该没问题」
**后果**：上生产才发现致命bug。
**正确做法**：AI生成的代码必须经过本体系所有门禁,无例外。

### ❌ 误区4：「测试用例越多越好」
**后果**：维护成本失控,测试本身成为负担。
**正确做法**：聚焦于"高价值场景",每个测试都要回答"为什么需要它"。

### ❌ 误区5：「自动化测试一次搭建,永久受益」
**后果**：测试逐渐失效,变成"虚假的安全感"。
**正确做法**：测试是活物,需要持续维护和演进。
