# 提交代码前检查清单

> **使用频率**：每次提交代码前（即每次让 Claude 写完代码、准备 `git commit` 之前）
> **预计耗时**：5-10 分钟
> **跳过的代价**：可能把 bug 带入主干，污染所有人的工作环境

---

## 为什么需要这个清单

在 AI 辅助开发模式下，最危险的不是"AI 写错代码"，而是 **"AI 写了看起来对的代码，但你没验证就提交了"**。一旦合并进主分支，这段代码会成为后续所有功能的基础——后面再发现问题，修复成本是现在的 10-100 倍。

**核心原则**：
- **永远不要"信任"AI 的代码**——验证它
- **永远不要"差不多就行"**——CI 会无情地告诉你不行
- **永远不要"明天再说"**——明天的你会忘记今天为什么这么写

## 第一关：本地基础检查（必做，约 2 分钟）

### ☐ 1.1 代码能运行起来

```bash
# 后端
cd backend && python -m uvicorn main:app --reload
# 在浏览器访问 http://localhost:8000/docs，确认服务起来

# 前端
cd frontend && npm run dev
# 在浏览器访问 http://localhost:5173，确认页面能打开
```

**判断标准**：
- ✅ 启动无报错
- ✅ 能访问到首页（或新功能页面）
- ❌ 启动报错 → **不要提交**，把错误信息发给 Claude 修复

### ☐ 1.2 你新写的功能能用

**手动操作一遍你刚做的功能**，至少覆盖：

- [ ] 正常路径走一遍（happy path）
- [ ] 试一个明显的错误输入（比如必填项留空）
- [ ] 试一个边界情况（比如输入超长字符串）

**如果是修 bug**：
- [ ] 复现原 bug 的步骤——确认 bug 不再出现
- [ ] 与 bug 相关的其他功能——确认没被破坏

> ⚠️ **常见陷阱**：业务人员经常只测"自己想要的路径"。AI 生成的代码，70% 的 bug 在异常路径上。**必须**主动尝试错误输入。

## 第二关：自动化检查（必做，约 1 分钟）

### ☐ 2.1 运行 pre-commit 钩子

如果你已经按照《工具链选型》配置了 pre-commit，这一步会在 `git commit` 时自动运行。如果没配置，手动跑一遍：

```bash
# 安装好 pre-commit 后（第一次需要）
pre-commit install

# 手动对所有暂存文件运行
pre-commit run

# 或者对所有文件全量运行
pre-commit run --all-files
```

**通过标准**：
- ✅ 所有钩子显示 `Passed`
- ❌ 任何 `Failed` → **不要提交**，把报错复制给 Claude

### ☐ 2.2 运行单元测试

```bash
# 后端
cd backend && pytest

# 前端
cd frontend && npm test
```

**通过标准**：
- ✅ 所有测试通过（绿色）
- ✅ 你新加的功能有对应测试
- ❌ 任何测试失败 → **不要提交**

> 💡 **如果没有为新功能写测试**：把代码贴给 Claude，使用 `prompts/04-测试生成提示词.md` 让它补全测试。**没有测试的代码不能进主分支**——这是铁律。

### ☐ 2.3 运行类型检查（TypeScript / Python typing）

```bash
# 后端
cd backend && mypy .

# 前端
cd frontend && npm run typecheck   # 或 tsc --noEmit
```

**通过标准**：
- ✅ 无类型错误
- ❌ 有类型错误 → 不要用 `# type: ignore` 或 `as any` 偷懒，让 Claude 真正修好

## 第三关：代码质量自检（强烈推荐，约 3 分钟）

### ☐ 3.1 让 Claude 审查它自己的代码

把你刚写的代码贴给 **新开的一个对话**（重要：必须新开对话，避免它"袒护"自己），使用 `prompts/03-代码审查提示词.md`。

让 Claude 自己审查，重点关注：

- 安全问题（SQL 注入、XSS、硬编码密钥）
- 错误处理是否完善
- 是否有遗漏的边界情况
- 是否符合 `CLAUDE.md` 的项目规范

**判断标准**：
- ✅ 报告中没有🔴红色（阻断性）问题
- ⚠️ 有🟠橙色（重要）问题 → 视情况修复，至少要在 commit message 里说明
- ✅ 🟡黄色（建议）问题可以记录到待办，不强制修复

> 💡 这一步看起来"麻烦"，但它能帮你拦住 80% 的低级问题。**它就是你的"虚拟代码审查同事"**。

### ☐ 3.2 检查"AI 常见错误模式"

对照 `templates/CLAUDE.md` 中的"项目特定的错误模式"章节，逐项检查：

- [ ] **没有伪造数据**：所有展示数据都来自真实接口/数据库，没有 `mock`、`example`、`placeholder` 类的硬编码
- [ ] **错误处理不是空的**：没有 `try { ... } catch { }` 或 `except: pass`
- [ ] **时区一致**：所有时间相关代码统一使用 UTC（DB 存储）和用户本地时区（展示）
- [ ] **没有 N+1 查询**：循环中没有数据库查询；列表渲染用 `JOIN` 或预加载
- [ ] **输入有验证**：所有来自用户/API 的输入都经过 Pydantic / Zod 等校验
- [ ] **没有泄露敏感信息**：日志中没有打印密码、token、信用卡号、身份证号
- [ ] **没有禁用安全检查**：没有 `verify=False`、`rejectUnauthorized: false`、`eslint-disable`、`@ts-ignore`

> ⚠️ **业务人员最容易忽略的**：第 3、4 条。时区错误和 N+1 查询不会立刻暴露，但会在用户量上来后变成灾难。

## 第四关：变更影响审查（必做，约 2 分钟）

### ☐ 4.1 看看你到底改了什么

```bash
# 查看暂存区的变更
git diff --cached

# 或者用 GUI 工具（推荐）：VS Code 的 Source Control 面板
```

**逐文件浏览，问自己**：

- [ ] **每一处改动我都能解释为什么**
- [ ] **没有意外修改的文件**（比如 Claude 顺手改了不相关的代码）
- [ ] **没有调试残留**：`console.log`、`print()`、`debugger`、`pdb.set_trace()`
- [ ] **没有注释掉的代码**（用 git history 而不是注释）
- [ ] **没有 TODO/FIXME** 留在关键路径上（如果留了，至少要建 issue 跟踪）

### ☐ 4.2 检查文件清单

- [ ] **没有提交不该提交的文件**：
  - `.env` 文件（含密钥）—— **绝对不能提交**
  - `node_modules/`、`__pycache__/`、`venv/`
  - 个人 IDE 配置（`.vscode/settings.json` 中的个人偏好）
  - 测试时生成的临时文件、日志文件、数据库文件

- [ ] **新增的依赖是必要的**：
  - 如果 `package.json` 或 `requirements.txt` 有变动
  - 检查新增的依赖是否真的需要
  - 检查依赖的下载量、最近更新日期、license（用 `npm view` 或 PyPI）
  - 触发 `prompts/06-架构守护提示词.md` 让 Claude 评估

### ☐ 4.3 敏感文件触发审查

如果你的改动涉及以下文件，**必须**让 AI 守护人审查后才能合并（参考 `templates/CODEOWNERS`）：

- [ ] 数据库迁移文件（`migrations/`、`alembic/`、`prisma/`）
- [ ] 认证、授权代码（`auth/`、`permissions/`、JWT 处理）
- [ ] 支付、计费相关代码
- [ ] CI/CD 配置（`.github/workflows/`、`Dockerfile`）
- [ ] `CLAUDE.md` 本身的修改
- [ ] 全局配置文件、环境变量管理

## 第五关：提交信息（必做，约 1 分钟）

### ☐ 5.1 写一个有意义的 commit message

**不好的例子**：
- ❌ `update`
- ❌ `fix bug`
- ❌ `Claude generated code`
- ❌ `修改了一些东西`

**好的例子**：
- ✅ `feat(auth): 添加邮箱验证码登录功能`
- ✅ `fix(order): 修复并发下单时库存超卖问题 #123`
- ✅ `refactor(api): 提取通用错误处理中间件`

**格式建议**（Conventional Commits）：

```
<类型>(<范围>): <简短描述>

<可选的详细说明，解释"为什么"，不是"做了什么">

<可选的 issue 引用>
```

**类型**：
- `feat`：新功能
- `fix`：修 bug
- `refactor`：重构（不改变功能）
- `test`：添加/修改测试
- `docs`：文档
- `chore`：杂项（依赖更新、配置等）
- `perf`：性能优化
- `style`：代码格式（不改逻辑）

### ☐ 5.2 关联需求/Bug

- [ ] 如果是开发新功能，commit message 中引用需求编号（如 `#REQ-123`）
- [ ] 如果是修 bug，引用 bug 编号（如 `#BUG-456`）
- [ ] 这能让你 6 个月后回看时，知道这段代码"为什么会这样写"

## 第六关：推送前最后一问（必做，约 30 秒）

在执行 `git push` 之前，问自己三个问题：

### ☐ 6.1 "如果这段代码上线后立刻出 bug，我能在 5 分钟内回滚吗？"

- ✅ 是 → 继续推送
- ❌ 否 → 检查是否：
  - 涉及数据库迁移（迁移要可逆，写好 down 脚本）
  - 涉及外部服务集成（要有降级方案）
  - 涉及缓存/消息队列结构变更（要有兼容期）

### ☐ 6.2 "这段代码会不会破坏其他人的工作环境？"

- ✅ 不会 → 继续推送
- ❌ 可能 → 检查是否需要：
  - 更新 `README.md` 中的环境搭建步骤
  - 更新 `.env.example` 文件
  - 在团队群里同步重要变更（如新增了环境变量、新增了依赖、修改了启动命令）

### ☐ 6.3 "我能跟非技术同事用一句话说清楚这次改了什么、为什么改吗？"

如果回答不出来，说明你自己其实没完全理解 Claude 写的代码。**这是最危险的状态**——

**应对**：
- 让 Claude 用通俗语言解释这段代码做了什么
- 让 Claude 给出一个"业务视角的描述"
- 把这个描述放进 commit message

---

## 推送之后：观察 CI（必做，约 2-5 分钟等待）

### ☐ 7.1 推送后立刻去 GitHub 看 CI 状态

```bash
git push
# 然后立刻打开 GitHub 仓库，进入 Actions 页面
```

**等到 CI 完整跑完**（通常 3-10 分钟）：

- ✅ 全绿 → 可以发起 Pull Request
- ❌ 有红 → **立刻**点进去看错误日志，把日志发给 Claude 修复
- ⚠️ **不要**用 `--no-verify` 跳过钩子推送
- ⚠️ **不要**直接推送到 `main` 分支（应该走 PR）

### ☐ 7.2 如果 CI 失败

1. **先看失败的具体步骤**（是单元测试？类型检查？安全扫描？）
2. **复制完整的错误日志**（不要只复制最后一行）
3. **新开一个 Claude 对话**，使用 `prompts/05-Bug诊断提示词.md`
4. **修复后重新运行第一关到第六关**——不能因为是"小修复"就跳过检查

> 💡 **不要**在 CI 反复失败的情况下硬怼修复。每次修复后都重新跑完整的检查清单。"小问题"叠加起来就是大灾难。

## 紧急情况：必须立刻提交怎么办？

**真正的紧急情况**（生产事故止血、安全漏洞修复）：

1. ✅ 第一关、第二关**绝对不能跳**（基础检查 + 自动化测试）
2. ⚠️ 第三关、第四关可以快速完成（5 分钟）
3. ✅ 第五关 commit message 必须明确标注 `[hotfix]` 或 `[emergency]`
4. ✅ 第六关至少快速思考一遍
5. ✅ 推送后**立刻**通知 AI 守护人/团队

**事后必做**：
- 24 小时内补全跳过的步骤（补测试、做完整审查）
- 写一份事故报告，归档到《生产事故应急清单》记录
- 如果是 AI 生成的代码导致的问题，更新 `CLAUDE.md`

## 常见反例（不要做的事）

### 反例 1："Claude 写的，应该没问题"

❌ **错误心态**。AI 生成的代码必须经过和人工代码同等强度的审查。AI 越自信，越要警惕——它经常一本正经地写出错的代码。

### 反例 2："测试我等做完功能再补"

❌ **永远不会补**。这是技术债的最大来源。**测试和功能代码必须同时提交**。如果觉得没时间写测试，那就是没时间做这个功能。

### 反例 3："这只是改了个小地方，应该不会影响其他功能"

❌ **小改动是 bug 的最大来源**，因为它绕过了所有警惕。**任何**改动都要走完整的清单。

### 反例 4："CI 失败是误报，我重试一下"

❌ **误报极少存在**。99% 的"误报"是真实问题。如果你怀疑是误报，让 Claude 分析一遍 CI 日志后再下结论。

### 反例 5："等会儿一起提交"

❌ **小步提交才安全**。一次提交一个功能/一个 fix。一次提交几十个文件、几千行变更，没人能审查清楚——包括你自己。

## 进阶：把这个清单自动化

随着你越来越熟练，可以把部分检查自动化：

1. **第二关全部** → 已经在 pre-commit 里
2. **第三关** → 写一个脚本，自动调用 Claude API 做代码审查（参考《工具链选型》的 Recommended 套餐）
3. **第四关 4.1** → 用 GUI Git 工具替代命令行，更直观
4. **第六关** → 用 `git push` hook 在推送前再问一次

但**第一关、第二关 1.2、第六关**必须人工完成——这是 AI 不可替代的判断力。
