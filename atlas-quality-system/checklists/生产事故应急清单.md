# 生产事故应急清单

> **使用时机**：生产环境出现任何异常时
> **核心原则**：**先止血，后追因**——优先恢复服务，事后再分析根因
> **禁忌**：在恐慌中操作、在没诊断清楚前修改生产代码

## 事故严重等级

在采取行动前，先判断严重等级。等级决定响应速度和处理方式。

### P0 - 灾难级
**特征**：
- 整个系统不可用，所有用户无法访问
- 大规模数据损坏 / 数据泄露
- 资金损失风险（支付错误、订单错误）
- 安全事件（被入侵、数据被外泄）

**响应时间**：5 分钟内开始处置
**通知范围**：所有相关方（团队、业务、法务、CEO）
**处理原则**：止血优先，不计代价

### P1 - 严重级
**特征**：
- 核心功能不可用（如登录、支付、下单）
- 大部分用户受影响（>30%）
- 性能严重退化（响应时间 > 10s）
- 错误率 > 10%

**响应时间**：15 分钟内开始处置
**通知范围**：团队 + 业务负责人
**处理原则**：止血优先

### P2 - 一般级
**特征**：
- 非核心功能不可用
- 少部分用户受影响（< 30%）
- 性能轻度退化
- 错误率 1-10%

**响应时间**：1 小时内开始处置
**通知范围**：团队 + AI 守护人
**处理原则**：可以诊断后再修复

### P3 - 轻微级
**特征**：
- 边缘功能问题
- 极少用户受影响
- UI 小问题、文案错误
- 不影响业务

**响应时间**：1 工作日内
**通知范围**：AI 守护人
**处理原则**：正常修复流程

## 第一阶段：发现与确认（前 5 分钟）

### Step 1：保持冷静

⚠️ **在生产环境慌乱操作是事故扩大的主要原因**。

- 深呼吸
- 不要立刻动手"修"
- 先想清楚：**到底发生了什么？**

### Step 2：快速诊断

**5 分钟内回答 5 个问题**：

#### 问题 1：到底是不是真的出事了？

不要被单一信号误导。综合判断：

- [ ] 监控大盘显示什么？（看 5-10 分钟趋势，不是单点）
- [ ] Sentry 错误率怎么样？
- [ ] 自己**手动测试**一下：能访问吗？能登录吗？关键功能能用吗？
- [ ] 有用户反馈吗？
- [ ] 是不是只是 CDN 缓存？是不是只是某地区？

> ⚠️ **常见误判**：
> - 监控告警了 → 不一定真出事，可能是误报
> - 有用户报错 → 不一定是系统问题，可能是用户网络/浏览器
> - Sentry 错误率高 → 看绝对值，可能基数太小

#### 问题 2：影响范围多大？

- [ ] 影响的用户比例？（10%? 50%? 100%?）
- [ ] 影响的功能？（核心 / 非核心？）
- [ ] 影响的地区？（全部 / 特定地区？）
- [ ] 影响的设备？（特定浏览器 / 移动端？）
- [ ] 是否有数据损坏？

#### 问题 3：什么时候开始的？

- [ ] 第一次报错时间？
- [ ] 此时距离上次发布有多久？
- [ ] 是渐进式恶化还是突然爆发？

> 💡 **黄金线索**：
> - "上次发布 30 分钟内出事" → 90% 概率是新版本引起的 → 优先回滚
> - "运行良好，突然挂了" → 可能是依赖的外部服务、数据量增长、缓存击穿
> - "渐进式变慢" → 可能是内存泄漏、数据库慢查询累积

#### 问题 4：是 P0/P1/P2/P3？

参考前文的等级判断标准。

#### 问题 5：现在最关键的事是什么？

- 如果是 **P0/P1** → **止血**（让用户能用）
- 如果是 **P2/P3** → **诊断**（搞清楚原因）

### Step 3：通知

根据等级通知对应人员：

```
[P0/P1 通知模板]
🚨 生产事故 - P{0/1}

事件：[一句话描述]
影响：[影响范围]
开始时间：[时间]
当前状态：处理中
处理人：[姓名]
临时方案：[已采取/计划采取]
预计恢复：[时间]
下次更新：[时间]
```

**不要做**：
- ❌ 含糊不清地说"出问题了"
- ❌ 等所有信息都搞清楚再通知（太晚了）
- ❌ 自己默默处理，不通知任何人

## 第二阶段：止血（紧急止损）

> **决策树**：
> - 上次发布 < 1 小时？→ 立刻**回滚**，先恢复服务
> - 上次发布 > 1 小时，但能定位到具体原因？→ **降级**或 **关 Feature Flag**
> - 完全找不到原因？→ **升级响应级别**，召集所有人

### 止血方案 A：回滚（最常用、最安全）

#### 适用情况
- 上次发布在 24 小时内
- 问题与发布时间高度吻合
- 能定位到大概是新版本引起的

#### 执行步骤

```bash
# 1. 确认要回滚到的版本（上一个稳定版本）
git log --oneline -10

# 2. 执行回滚部署（具体命令取决于部署方式）
# 示例：Kubernetes
kubectl rollout undo deployment/atlas-backend
kubectl rollout undo deployment/atlas-frontend

# 示例：Docker Compose
docker-compose pull
docker-compose up -d

# 示例：Vercel / Netlify
vercel rollback
# 或在 dashboard 点击"Promote to Production"上一个版本
```

#### 回滚检查项

- [ ] 回滚后服务起来了吗？
- [ ] 健康检查通过吗？
- [ ] **数据库迁移**怎么办？
  - 如果新版本只增加字段：旧版本可以兼容（OK）
  - 如果新版本删除/重命名字段：旧版本会报错（**需要先回滚 DB**）
  - 如果新版本改了字段类型：可能需要数据修复
- [ ] 错误率回归正常了吗？
- [ ] 用户能正常访问了吗？

⚠️ **回滚陷阱**：
- 如果回滚后还是有问题，**不要继续回滚更多版本**，可能问题不在代码
- 数据库迁移很难回滚——务必在每次发布前确认迁移可逆
- 如果回滚需要 > 30 分钟，考虑改用降级方案

### 止血方案 B：关 Feature Flag

#### 适用情况
- 问题定位到某个新功能
- 该功能有 Feature Flag 控制
- 关闭后不影响其他功能

#### 执行步骤

```bash
# 1. 登录 Feature Flag 管理面板（Unleash / LaunchDarkly）
# 2. 找到对应的 Flag
# 3. 关闭它（或设为 0% 流量）
# 4. 等待生效（通常 < 1 分钟）
```

#### 检查项
- [ ] Flag 已关闭？
- [ ] 配置已生效？
- [ ] 错误率回归正常？

> 💡 **这就是为什么所有新功能都要包 Feature Flag**——出事时能快速止血而不需要回滚整个版本。

### 止血方案 C：降级

#### 适用情况
- 某个功能严重影响整体（如某个 API 拖垮整个服务）
- 关掉它能让其他功能恢复

#### 执行步骤

```python
# 示例：临时降级某个慢 API
@app.get("/api/expensive-endpoint")
async def expensive_endpoint():
    # 临时返回降级响应
    return {"degraded": True, "message": "功能维护中，请稍后再试"}
    # 原代码注释掉

# 部署这个临时改动
```

或者通过配置开关：

```python
if config.FEATURE_X_ENABLED:
    return await expensive_logic()
else:
    return cached_or_fallback_response()
```

### 止血方案 D：限流 / 熔断

#### 适用情况
- 流量过载（被刷、突发流量）
- 某个下游服务挂了，自己被拖垮

#### 执行步骤

```bash
# 在 Nginx / 网关层加限流
# Cloudflare：开启 "Under Attack Mode"
# AWS WAF：临时加 rate limit rule
# 应用层：临时降低限流阈值
```

### 止血方案 E：扩容

#### 适用情况
- 容量不足（CPU / 内存 / 数据库连接）
- 流量正常但资源不够

#### 执行步骤

```bash
# Kubernetes
kubectl scale deployment/atlas-backend --replicas=10

# 数据库连接池扩大（修改配置后重启）
```

⚠️ **扩容陷阱**：
- 扩容不能解决代码 bug
- 数据库扩容很难（需要主从切换）
- 临时扩容后记得**事后还原**

### 止血方案 F：完全停服

#### 适用情况
- 数据正在被损坏
- 安全事件正在进行中
- 任何"不停服会让事情更糟"的情况

#### 执行步骤

```bash
# 在负载均衡层把所有流量切到维护页面
# 或者：直接停掉应用进程
# 然后挂上"维护中"页面
```

⚠️ 这是核选项，慎用。但**有些情况必须用**：
- 检测到数据库被批量删除
- 检测到密钥泄露
- 检测到 SQL 注入正在被利用

## 第三阶段：诊断（找根因）

> **此阶段的目标**：找出**真正的根因**，不是表面症状。
> **铁律**：在没诊断清楚前，不要修改生产代码。

### Step 1：收集证据

**日志**：
```bash
# 查看最近的错误日志
kubectl logs -l app=atlas-backend --tail=1000 | grep ERROR
# 或者去日志聚合系统（Loki / CloudWatch）查询
```

**Sentry**：
- 看错误堆栈
- 看影响的用户数和频次
- 看关联的 Release（哪个版本开始的？）
- 看 Breadcrumbs（错误前发生了什么？）

**监控指标**：
- CPU、内存、磁盘、网络
- 数据库 QPS、连接数、慢查询
- 缓存命中率
- 队列堆积

**用户反馈**：
- 客服收到的问题
- 用户在社交媒体的反馈

### Step 2：5-Why 分析（让 Claude 帮忙）

把所有证据丢给 Claude，使用 `prompts/05-Bug诊断提示词.md`：

```
症状：[一句话描述]
错误日志：[贴日志]
监控截图：[贴截图或描述]
最近变更：[最近 24 小时的所有发布、配置修改]

请用 5-Why 分析法找出根因：
1. 为什么出现这个症状？
2. 为什么会出现 1 中的原因？
3. 为什么会出现 2 中的原因？
4. 为什么会出现 3 中的原因？
5. 为什么会出现 4 中的原因？

最终根因是什么？
```

### Step 3：常见根因模式

#### 模式 1：发布相关
- 新代码引入 bug
- 数据库迁移有问题
- 环境变量配置错误
- 依赖版本不兼容

#### 模式 2：依赖问题
- 第三方服务挂了（支付、邮件、短信）
- DNS 解析问题
- SSL 证书过期
- 网络故障

#### 模式 3：容量问题
- 流量突增（活动、被刷）
- 数据量增长（表越来越大）
- 内存泄漏累积
- 连接池耗尽

#### 模式 4：数据问题
- 异常数据触发 bug（特殊字符、超长字段、null 值）
- 缓存与数据库不一致
- 并发导致的数据竞争
- 时区/时间问题

#### 模式 5：基础设施问题
- 物理机 / 云主机故障
- 磁盘满了
- 数据库主从延迟
- 中间件挂了（Redis / MQ）

### Step 4：复现（如果可能）

在 staging 环境尝试复现：

- 用相同的输入触发
- 用相同的并发量
- 用相同的数据状态

**复现成功** = 根因基本确认 → 进入修复阶段
**复现失败** = 可能是环境因素或概率事件 → 加强监控，继续观察

## 第四阶段：修复

### 原则 1：在 staging 修，不在生产修

❌ **永远不要直接修改生产代码**（除非是 P0 灾难级且没有其他选择）
✅ 在 staging 环境修复 → 验证 → 走正常发布流程

### 原则 2：修复也是变更，也要审查

紧急修复**也必须**经过：
- AI 代码审查（用 `prompts/03-代码审查提示词.md`）
- AI 守护人审查
- 测试

只是流程加速：从 1-2 天压缩到 1-2 小时。

### 原则 3：写测试防止复发

**任何**事故的根因，都要写一个**自动化测试**来防止它复发。

```python
def test_bug_xxx_does_not_regress():
    """
    Regression test for incident YYYY-MM-DD-N.

    Root cause: [简述]
    Symptom: [症状]
    Fix: [简述修复]
    """
    # 用导致 bug 的输入触发
    result = service.process(buggy_input)
    # 验证不再出 bug
    assert result.is_correct
```

这个测试要永久保留，并在 commit message 里引用事故编号。

### 复盘原则

✅ **对事不对人**：不追究个人责任，追究流程缺陷
✅ **找系统问题**：不止于"小王手抖了"，要问"为什么手抖会导致事故？为什么没有防御？"
✅ **改进可执行**：每个改进项必须有 owner、有截止日期、可验证
❌ **不要泛泛而谈**："以后大家小心点" = 没有改进
❌ **不要文化报应**：不要让人因为坦诚承认错误而受惩罚

## 特殊场景应急

### 场景 1：数据库被误删/误改

**绝不**：
- ❌ 立刻在生产数据库上"撤销"
- ❌ 不停止应用就开始恢复
- ❌ 不备份当前状态就回滚

**应该**：
1. **立刻停止写入**（停应用 / 维护模式 / 只读模式）
2. **保留现场**（当前数据库状态备份一份，作为"事故证据"）
3. **从最近备份恢复**到一个**新数据库实例**
4. **比对差异**，决定如何合并丢失的数据
5. **业务方确认**后切换

### 场景 2：密钥泄露

**优先级最高**：
1. **立刻撤销**泄露的密钥（API key、token、密码）
2. **生成新密钥**并部署
3. **审查日志**：泄露期间是否被滥用？
4. **通知**所有相关方（包括用户，如果涉及用户数据）
5. **法务介入**（如有合规要求）
6. **事后**：审查为什么泄露（代码？配置？日志？）

### 场景 3：被 DDoS

**应对**：
1. 启用 Cloudflare "Under Attack Mode" 或类似服务
2. 在 WAF 层加限流规则
3. 临时扩容
4. **不要**给攻击者支付任何费用
5. 报警（如果是大规模有组织攻击）

### 场景 4：数据正在持续损坏

**特征**：每分钟都有新的数据被错误处理
**应对**：
1. **立刻停止应用**（数据保护优先于服务可用）
2. 进入维护模式
3. 评估损坏范围
4. 修复代码
5. 修复已损坏数据
6. 恢复服务

### 场景 5：第三方服务挂了

**应对**：
1. 确认是否真的挂了（有时是自己的网络/配置问题）
2. 启用降级方案（如果有）
3. 通知用户"由于第三方服务问题，X 功能暂时不可用"
4. **不要**反复重试导致雪崩
5. 等第三方恢复后验证

## 预防胜于治疗

最好的事故应急 = 不出事故。投资于：

1. **混沌工程**：定期主动制造小故障，验证应对能力
2. **应急演练**：每季度演练一次"如果 X 挂了怎么办"
3. **可观测性**：投入足够的监控/告警/日志
4. **Feature Flag**：所有新功能都要可独立开关
5. **回滚演练**：每月真实回滚一次（在 staging）
6. **文档化**：本清单 + Runbook + 应急工具包
