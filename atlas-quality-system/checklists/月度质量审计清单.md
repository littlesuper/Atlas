# 月度质量审计清单

> **使用频率**：每月最后一个工作日（或下月第一个工作日）
> **执行人**：AI 代码守护人 + 业务负责人
> **耗时**：3-4 小时
> **输出**：一份月度质量报告 + 下月改进计划

---

## 这份清单的目的

如果只是机械地按照《工作流程》和检查清单做事，质量保障体系会僵化、过时、最终失效。这份清单的核心是：

> **让质量体系本身具备自我进化能力**

每月一次的全面审视，回答四个问题：

1. **这个月的质量数据怎么样？**（事实层）
2. **哪里做得好，哪里出了问题？**（分析层）
3. **流程/工具/规范需要哪些调整？**（改进层）
4. **下个月的优先事项是什么？**（行动层）

---

## 第一部分：质量数据收集（约 1 小时）

### 1.1 测试质量数据

从 CI 系统（GitHub Actions）和测试报告中提取本月数据：

- [ ] **测试通过率**：每天的 CI 通过率（趋势图）
  - 目标：≥ 95%
  - 红线：< 90% 需要重点改进
- [ ] **代码覆盖率**：行覆盖、分支覆盖、突变测试分数
  - 趋势：上升 / 持平 / 下降？
  - 哪些模块覆盖率最低？
- [ ] **测试数量**：单元、集成、E2E 各多少
  - 测试增长 vs 代码增长是否匹配？
- [ ] **测试执行时间**：CI 全流程耗时
  - 是否在退化（变慢）？
  - 哪些测试最慢？
- [ ] **Flaky 测试**：本月被标记为 flaky 的测试清单
  - 处理状态：已修复 / 已跳过 / 待处理
  - 占比：flaky 测试 / 总测试数

### 1.2 代码质量数据

- [ ] **静态扫描问题**：本月新增 vs 修复
  - 高严重 / 中严重 / 低严重 各多少
  - 趋势：在累积还是在清理
- [ ] **安全扫描问题**：CodeQL、Snyk、Bandit 报告
  - 高危漏洞数量
  - 平均修复时间
- [ ] **依赖漏洞**：依赖审计结果
  - 待更新依赖数量
  - 已知漏洞依赖数量
- [ ] **技术债清单**：`TODO`/`FIXME`/`XXX` 总数
  - 在增加还是减少
  - 哪些是关键路径上的

### 1.3 AI 生成代码质量数据

> 这是 AI 驱动开发场景下**最关键**的指标——它直接反映 AI 协作的健康度。

- [ ] **AI 代码审查拦截率**：CI 中"AI Code Review"环节拦了多少 PR
  - 趋势：在增加（AI 越来越严）还是减少（AI 越来越宽松）
  - 拦截理由分布（安全/性能/可读性/规范）
- [ ] **CLAUDE.md 违反次数**：被 CI 检测到的违反规范的次数
  - 哪些规范被违反最多
  - 是规范不合理，还是 AI 没遵循
- [ ] **AI 生成的代码 vs 人工修改的比例**：
  - 让 AI 一次性写对的占多少
  - 需要多轮迭代才行的占多少
  - 不得不人工修改的占多少
- [ ] **重复 bug 模式**：本月出现的重复性 bug
  - 比如"AI 又忘了处理空数组" → 应该更新 CLAUDE.md 的反模式清单

### 1.4 生产质量数据

- [ ] **事故数量**：P0、P1、P2、P3 各多少
- [ ] **MTTR（平均修复时间）**：从发现到恢复
  - 目标：P0 < 30 分钟，P1 < 2 小时
- [ ] **缺陷逃逸率**：上线后才发现的 bug / 总 bug
  - 目标：< 5%
  - 红线：> 15% 说明测试不充分
- [ ] **回滚次数**：本月发布了多少次，回滚了多少次
  - 回滚率：回滚 / 发布
- [ ] **Sentry 错误**：
  - 总错误数量趋势
  - 唯一错误数量（去重）
  - 影响用户数量
  - Top 10 错误清单
- [ ] **性能指标**：
  - P95 / P99 响应时间趋势
  - 慢查询数量
  - 错误率趋势

### 1.5 业务影响数据

- [ ] **用户反馈**：客服收到的问题数量
  - 按类型分类（功能问题 / UX 问题 / 性能问题）
  - 同一问题被多人提及的（说明影响面大）
- [ ] **业务关键指标**：
  - 注册转化率
  - 核心功能完成率
  - 留存率
  - 是否因质量问题导致下滑

### 1.6 流程效率数据

- [ ] **从需求到上线的周期**：
  - 平均需求 → 上线天数
  - 在哪个阶段最耗时
- [ ] **PR 数据**：
  - 平均 PR 大小（行数）
  - 平均 PR 审查时间
  - 平均合并时间
- [ ] **代码评审参与度**：
  - AI 守护人覆盖率（多少 PR 被审了）
  - 审查质量（review 留下了多少有价值的评论）

## 第二部分：成功与失败案例分析（约 30 分钟）

### 2.1 三个最成功的案例

挑选本月**做得最好**的三个案例：

```
案例 #1：[简述]
- 做了什么：
- 为什么成功：
- 哪些做法值得复制：
- 是否可以制度化（写进流程/清单）：

案例 #2：...
案例 #3：...
```

> **目的**：放大成功经验，形成正反馈。

### 2.2 三个最失败的案例

挑选本月**最有教训**的三个案例（可以包括事故、严重 bug、重做的功能、被骂的功能等）：

```
案例 #1：[简述]
- 出了什么问题：
- 根本原因：
- 当时的检查清单/流程为什么没拦住：
- 应该如何改进：
- 是否需要更新 CLAUDE.md / 检查清单：

案例 #2：...
案例 #3：...
```

> **目的**：把教训沉淀成体系，避免重蹈覆辙。

### 2.3 "差点出事但没出"清单

最容易被忽视、但其实最有价值的——**虚惊一场**：

- 哪些问题在 staging 被拦下来了？（说明 staging 有用）
- 哪些问题在 PR review 被发现了？（说明 review 有用）
- 哪些问题在 pre-commit 被拦下来了？（说明工具链有用）
- 哪些问题如果没被拦住，会造成什么后果？

> **目的**：让团队意识到"看不见的防线"在发挥作用，强化对体系的信心。

## 第五部分：下月计划（约 20 分钟）

### 5.1 改进项优先级排序

把上面所有改进项整合到一张表，按 ICE 评分排序：

```
| 改进项 | Impact (1-10) | Confidence (1-10) | Ease (1-10) | ICE 总分 | 排序 |
|--------|---------------|-------------------|-------------|---------|------|
| ...    | ...           | ...               | ...         | ...     | ...  |
```

> ICE = Impact（影响）× Confidence（确信度）× Ease（容易度）
> 高 ICE = 优先做

### 5.2 选定 Top 3-5 个改进项

从优先级排序中选 3-5 个本月**必做**的改进项：

```
改进项 #1：
- Owner：
- 截止日期：
- 验收标准：
- 风险：

改进项 #2：...
改进项 #3：...
```

> ⚠️ **重要**：不要贪多。3-5 个比 10 个更有可能真正落地。

### 5.3 设定下月质量目标

基于本月数据，设定下月**可量化**的目标：

- [ ] 测试通过率：本月 __% → 下月目标 __%
- [ ] 代码覆盖率：本月 __% → 下月目标 __%
- [ ] 缺陷逃逸率：本月 __% → 下月目标 __%
- [ ] MTTR：本月 __ 分钟 → 下月目标 __ 分钟
- [ ] 上线频率：本月 __ 次 → 下月目标 __ 次
- [ ] 回滚率：本月 __% → 下月目标 __%

### 5.4 风险预警

- [ ] 哪些指标在恶化？

## 持续优化建议

### 第一个月：先跑起来
不追求完美，先把所有数据收集流程建立起来。即使数据不全，也要走完整流程一遍。

### 第三个月：开始有趋势
有了 3 个月数据，趋势就显现了。重点关注**变化方向**而不是绝对值。

### 第六个月：调整体系
3-6 个月足够看出哪些清单/流程是真有用的，哪些是形式主义。大胆删减无用内容。

### 第十二个月：体系自洽
1 年后，质量体系应该已经"长成"自己的样子，与项目特点高度匹配。这时候**写一份"我们的质量哲学"**，沉淀成知识资产。

---

## 这份清单本身的迭代

这份清单也需要每年重新审视：

- [ ] 哪些数据收集没人在看？（删掉或自动化）
- [ ] 哪些维度漏了？
- [ ] 哪些步骤太繁琐？

**质量审计的目标不是审计本身**——而是让 Atlas 越来越好。如果这份清单变成了形式主义，立刻**改掉**它。
