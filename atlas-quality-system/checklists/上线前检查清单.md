# 上线前检查清单（生产发布 Go/No-Go）

> **使用时机**：每次发布到生产环境前 24-48 小时启动；正式发布前 1 小时再过一遍
> **预计耗时**：首次完整执行 4-8 小时；熟练后 1-2 小时
> **决策权**：最终 Go/No-Go 由 AI 代码守护人 + 业务负责人共同决定
> **跳过的代价**：上线后出严重故障，修复成本是上线前发现的 100-1000 倍

---

## 这份清单的设计逻辑

上线前的检查必须是 **"系统性"的**，因为一旦上线，影响的是真实用户、真实数据、真实金钱。这份清单按照"由内到外"的顺序设计：

1. **代码层面**：代码本身是否健康
2. **测试层面**：是否充分验证
3. **基础设施层面**：环境、配置、部署是否就绪
4. **可观测性层面**：出问题时能不能发现
5. **应急层面**：出问题时能不能恢复
6. **业务层面**：业务流程、用户沟通、合规
7. **决策层面**：综合评估、Go/No-Go

**核心原则**：
- 任何一项⚠️或❌都要明确说明"为什么允许带病上线"
- 即使首次上线，也要假装"上线后会出事"——准备好应对
- **怀疑就是不上**——上线没有"先试试"，只有"全力以赴"

## 第一部分：代码就绪度（约 30 分钟）

### 1.1 代码冻结状态

- [ ] 已确定本次发布的代码版本（git commit hash）
- [ ] 该版本之后**没有**任何新功能合并到发布分支
- [ ] 有完整的 Release Notes（功能列表、Bug 修复、Breaking Changes）
- [ ] Release Notes 中**明确标注**了对用户/业务的影响

### 1.2 代码健康度

- [ ] 主分支 CI **完全绿色**（最近 7 天没有红色失败）
- [ ] 静态扫描无 🔴 阻断性问题
- [ ] 安全扫描（CodeQL/Snyk/Bandit）无高危漏洞
- [ ] 依赖审计（npm audit / pip-audit）无 critical/high 漏洞
- [ ] 没有遗留的 `TODO/FIXME/XXX` 在关键路径上
- [ ] 没有任何 `console.log`、`print()`、`debugger`、`pdb.set_trace()`
- [ ] 没有任何被注释掉的"以防万一"代码
- [ ] 没有任何 `@ts-ignore`、`# type: ignore`、`eslint-disable` 是新增的

### 1.3 代码审查完整性

- [ ] 本次发布涉及的**所有**变更都经过了 AI 代码守护人的审查
- [ ] 高风险文件（数据库迁移、认证、支付）经过了**双人审查**
- [ ] 所有🟠橙色（重要）问题都已修复或有明确说明
- [ ] PR 评论中所有遗留的讨论已闭环

### 1.4 变更影响分析

让 Claude 完成《架构守护提示词》分析，输出本次发布的：

- [ ] 影响的功能模块清单
- [ ] 影响的数据库表清单
- [ ] 影响的对外 API 清单（含版本兼容性）
- [ ] 新引入的依赖清单
- [ ] 配置变更清单
- [ ] 性能影响评估（响应时间、内存、数据库负载）

## 第二部分：测试就绪度（约 1-2 小时）

### 2.1 自动化测试覆盖

- [ ] 单元测试覆盖率 ≥ 80%（核心业务逻辑 ≥ 95%）
- [ ] 集成测试覆盖了所有关键 API 端点
- [ ] E2E 测试覆盖了所有核心用户旅程：
  - [ ] 注册 / 登录 / 退出
  - [ ] 找回密码
  - [ ] 主要业务流程（按业务定义）
  - [ ] 支付流程（如有）
  - [ ] 数据导入/导出（如有）
- [ ] 突变测试（mutation testing）分数 ≥ 60%（如已配置）

### 2.2 测试结果审查

- [ ] **没有**被跳过的测试（`@skip`、`xit`、`it.skip`）
- [ ] **没有**被标记为 flaky 的测试在关键路径上
- [ ] 最近 7 天测试通过率稳定在 95%+
- [ ] 性能基准测试结果与上次发布对比，**没有**显著退化（>20%）

### 2.3 手工测试

由 AI 守护人 + 业务负责人共同执行：

- [ ] 在 staging 环境完整跑过一遍**核心业务流程**
- [ ] 测试过**主要浏览器**：Chrome、Safari、Firefox（至少最新版）
- [ ] 测试过**移动端**：iOS Safari、Android Chrome
- [ ] 测试过**响应式布局**：手机、平板、桌面三个断点
- [ ] 测试过**真实数据**（脱敏后的生产数据样本）
- [ ] 测试过**异常场景**：网络断开、超时、错误响应
- [ ] 测试过**权限边界**：未登录、不同角色、跨用户访问

### 2.4 用户体验检查

- [ ] 所有页面无明显视觉错位
- [ ] 所有交互有合理的反馈（Loading、Success、Error）
- [ ] 所有错误信息对用户友好（不暴露技术栈）
- [ ] 文案没有错别字、语法错误、遗漏占位符（如 `Hello, {name}!`）
- [ ] 关键操作有二次确认（删除、支付、不可逆操作）
- [ ] 表单验证及时、清晰、可恢复

### 2.5 可访问性检查

- [ ] axe-core 自动扫描无 critical 问题
- [ ] 关键页面用键盘可以完整操作
- [ ] 所有图片有 `alt` 属性
- [ ] 颜色对比度符合 WCAG AA
- [ ] 表单元素都有关联的 `<label>`

## 第三部分：基础设施就绪度（约 1-2 小时）

### 3.1 环境配置

- [ ] 生产环境的所有环境变量已配置（用 `.env.example` 比对）
- [ ] **没有**任何环境变量值是从开发/测试环境复制的（如 `JWT_SECRET=test`）
- [ ] 所有密钥都通过密钥管理服务（AWS Secrets Manager / Vault）注入，不在代码中
- [ ] 数据库连接串、Redis 连接串等指向**生产实例**，不是 staging
- [ ] CORS 配置正确（不要 `*`）
- [ ] CSP（Content Security Policy）配置完整
- [ ] HTTPS 已启用，证书有效期 > 30 天
- [ ] HSTS 已启用

### 3.2 数据库

- [ ] 数据库迁移脚本已经在 staging 环境**完整跑过一遍**
- [ ] 迁移脚本是**可逆的**（有 down migration）
- [ ] **大表迁移**（>100万行）已规划好执行窗口
- [ ] 数据库已做**全量备份**，备份时间 < 24 小时前
- [ ] 备份恢复演练**最近 30 天内**做过一次
- [ ] 数据库连接池大小合理（不会耗尽）
- [ ] 慢查询日志已开启
- [ ] 数据库账号权限**最小化**：应用账号没有 `DROP`、`TRUNCATE` 权限

### 3.3 外部服务依赖

逐一检查每个依赖的外部服务：

- [ ] 邮件服务（SendGrid / Mailgun）：API key 有效、额度充足
- [ ] 短信服务（Twilio / 阿里云短信）：账户有钱、限流配置
- [ ] 支付服务（Stripe / 微信支付）：生产 key 已配置、回调 URL 正确
- [ ] 对象存储（S3 / OSS）：bucket 已创建、权限正确
- [ ] CDN：已配置缓存策略
- [ ] 第三方 API：限流配置、降级方案
- [ ] DNS：所有需要的域名解析正确

### 3.4 部署流程

- [ ] 部署脚本已在 staging 跑通至少 3 次
- [ ] 部署是**幂等的**（重复执行不会出问题）
- [ ] 部署可以**回滚**（有明确的回滚命令/脚本）
- [ ] 部署有**健康检查**（`/health` endpoint 返回 200 才算成功）
- [ ] 部署有**滚动更新**机制（不会一次性把所有实例替换）
- [ ] 部署有**Canary 阶段**（先 5% 流量，观察 30 分钟，再放量）

### 3.5 性能基准

- [ ] 在 staging 跑过**负载测试**（k6 / Locust），目标负载下：
  - [ ] P95 响应时间 < 500ms（核心 API）
  - [ ] P99 响应时间 < 2s
  - [ ] 错误率 < 0.1%
  - [ ] CPU 使用率 < 70%
  - [ ] 内存使用率 < 70%
- [ ] 没有内存泄漏（持续运行 24 小时不增长）
- [ ] 数据库慢查询已优化（无 > 1s 的查询在关键路径）

## 第四部分：可观测性就绪度（约 30 分钟）

### 4.1 日志

- [ ] 所有关键路径有结构化日志
- [ ] 日志包含 trace_id / request_id（可追踪一次请求的全链路）
- [ ] 日志**不包含**：密码、token、信用卡号、身份证号、完整邮箱
- [ ] 日志级别合理：生产环境默认 INFO，可动态调整到 DEBUG
- [ ] 日志聚合系统（Loki / CloudWatch / Datadog Logs）已配置
- [ ] 日志保留策略已配置（如 30 天热存储 + 90 天冷存储）

### 4.2 指标（Metrics）

- [ ] 业务指标已埋点（注册数、订单数、关键转化率）
- [ ] 技术指标已采集（QPS、响应时间、错误率、资源使用率）
- [ ] Dashboard 已搭建（业务大盘 + 技术大盘）
- [ ] AI 守护人能在 1 分钟内打开 Dashboard 看到关键指标

### 4.3 错误追踪（Error Tracking）

- [ ] Sentry / Bugsnag 已集成（前端 + 后端）
- [ ] 错误能正确上报（在 staging 触发一个测试错误验证）
- [ ] 错误**source map** 已上传（前端能看到原始代码位置）
- [ ] 错误已配置**用户上下文**（能看到是哪个用户遇到的）
- [ ] 错误已配置**Release 标签**（能看到是哪个版本引入的）

### 4.4 告警

- [ ] **业务告警**已配置：
  - [ ] 注册失败率 > 5%
  - [ ] 支付失败率 > 1%
  - [ ] 关键页面 5 分钟内 0 访问（系统挂了）
- [ ] **技术告警**已配置：
  - [ ] 错误率 > 1%
  - [ ] P95 响应时间 > 1s
  - [ ] CPU > 80%
  - [ ] 内存 > 80%
  - [ ] 磁盘 > 80%
  - [ ] SSL 证书 < 30 天到期
- [ ] 告警有**分级**：紧急（电话/短信）vs 一般（邮件/Slack）
- [ ] 告警有**值班人**（明确谁会收到、谁会响应）
- [ ] 告警**不会风暴**（同类问题去重、抑制）

### 4.5 健康检查

- [ ] `/health` 端点返回 200
- [ ] `/health` 检查项包含：数据库连接、Redis 连接、关键依赖
- [ ] 负载均衡器/Kubernetes 配置了健康检查（不健康自动摘掉）

## 第五部分：应急就绪度（约 30 分钟）

### 5.1 回滚方案

- [ ] **回滚命令**已写在文档里，AI 守护人 5 分钟内能执行
- [ ] **回滚演练**做过（在 staging 真的回滚一次）
- [ ] **数据库迁移回滚**有明确方案：
  - [ ] 如果可回滚 → 准备 down migration 脚本
  - [ ] 如果不可回滚（如删字段、改类型）→ 确认有备份，且接受"只能向前修复"
- [ ] **前端回滚** vs **后端回滚** 的兼容性已验证

### 5.2 Feature Flag

- [ ] **新功能**都包裹在 Feature Flag 里
- [ ] Feature Flag 系统（Unleash / LaunchDarkly）已就绪
- [ ] 默认状态是 **关闭** 或 **小流量灰度**

### 5.3 应急联系人

- [ ] 明确**值班人**（谁在上线后 24 小时内随时响应）
- [ ] 明确**升级路径**（值班人解决不了 → 找谁）
- [ ] 联系方式**冗余**（手机 + 微信 + Slack，至少两种）

### 5.4 应急预案

- [ ] 已演练过"服务挂了怎么办"
- [ ] 已演练过"数据库挂了怎么办"

- [ ] **写操作有事务保护**（不会写一半挂掉）

- [ ] **删除是软删除**（关键业务数据不真删）

## Go / No-Go 决策框架

### Go 的条件（**必须全部满足**）

✅ 所有🔴红色项已完成
✅ 所有🟠橙色项已完成或有明确说明
✅ 测试通过率 ≥ 95%
✅ 没有已知的高危/严重 bug
✅ 监控、告警、回滚方案就绪
✅ AI 守护人和业务负责人都签字

### No-Go 的信号（**任何一个**）

❌ 安全扫描有未修复的 high/critical 漏洞
❌ 性能在负载下严重退化
❌ 监控/告警未就绪
❌ 回滚方案未验证
❌ 数据库迁移未做过 dry-run
❌ 关键依赖（支付/认证）的提供商有已知问题
❌ AI 守护人有"说不清的不安"——**这是最重要的信号**

### 介于之间：Go with Conditions

⚠️ 允许带病上线，但必须：
- 明确文档记录"哪些方面没准备好"
- 明确补救计划和时间
- 明确风险接受人
- 配置更密集的监控和告警
- 缩小发布范围（如只灰度 5%）

## 修订历史

| 日期 | 版本 | 修改内容 |
|------|------|---------|
| 初始版本 | v1.0 | 创建 |

> **维护人**：AI 代码守护人
> **每次发布后必须更新**：根据本次发布发现的问题，补充检查项。
> **半年大版本**：完整重写一遍，删除已自动化的项目，新增浮现的风险。
